# Path of Cultivation — технический проект

Дата: 14 октября 2026 года. Цель: RimWorld 1.7 unstable, далее проверенная стабильная 1.7.
Документ описывает архитектуру и план проверок. Минимальный bootstrap подтверждён разработчиком; работа игровых механик этим не подтверждена.

## 1. Статус технических сведений

**Подтверждено официально:** Ludeon объявила 12 октября переход на Waylith и доступность unstable; заявлена широкая совместимость старых модов. Это не гарантирует загрузку конкретной DLL. Источник: [анонс Ludeon](https://ludeon.com/blog/2026/10/announcing-the-waylith-engine-and-update-1-7/).

**Подтверждено первичным проектом стороннего разработчика:** сборка FasterGameLoading для 1.7 использует .NET 10, игровые Assembly-CSharp.dll, UnityStubs.dll, Waylith.dll и установленный Harmony. Это практический пример, не официальный контракт Ludeon: [репозиторий](https://github.com/mushroomTW/FasterGameLoading---Continued).

**Применено в bootstrap:** SDK .NET 10, SDK-style csproj, TargetFramework=net10.0; минимальный мод собран в Docker и загружен в RimWorld 1.7 unstable с WaylithCLR (по согласованному заданию). SDK закрепить точной установленной версией через global.json; Docker-образ — digest. LangVersion без preview. Runtime и SDK — разные вещи: SDK собирает библиотеку, игра загружает её своим runtime. Не паковать runtime вместе с модом.

**Требует локальной проверки:** точный build игры, runtimeconfig, расположение и версии DLL, функциональные API механик и UI. Загрузка минимальной net10.0 DLL подтверждена; Harmony не входит в MVP и проверяется лишь при отдельном решении о патче. Старый net472, пути Unity Managed и UnityEngine DLL из 1.6 не использовать по инерции. При противоречии источника локальному build сначала обновить RESEARCH и решение, затем продолжать.

Harmony 3.0.0-rc.2 существует как prerelease по [релизам автора](https://github.com/pardeike/Harmony/releases). Это не доказывает обязательность этой версии для всякого мода 1.7. Базовый MVP проектируется без Harmony. Если патч понадобится, проверить конкретную Workshop-сборку 1.7, pin совместимой версии и load order; не поставлять свою копию 0Harmony.dll.

## 3. Направление зависимостей

- PathOfCultivation.Core: чистые модели, расчёты, проверки условий. Нет Verse, RimWorld, Waylith, UnityStubs, Harmony, DLC.
- PathOfCultivation.RimWorld: Def, Jobs, Hediffs, UI, Scribe, перевод времени и игровых данных в модель Core.
- PathOfCultivation.Integration.*: отдельные поздние пакеты; зависят от базы и соответствующего DLC.
- PathOfCultivation.Core.Tests: проверяет расчёты без игры; version smoke tests выполняются на Windows.

UI вызывает сервисы адаптера; сервис строит snapshot и передаёт его Core; результат применяется к пешке на игровом потоке. Core никогда не ищет Pawn, не обращается к DefDatabase и не вызывает игровой RNG.

Для MVP достаточно двух production-проектов и одного проекта тестов. Не нужны DI-контейнер, event bus, ECS, reflection-регистрация всех обработчиков или отдельный публичный SDK.

## 5. Данные и Def

Все имена собственных классов ниже — предложение проекта. Наличие одноимённых vanilla API не подразумевается.

| Def | Минимальные поля | Проверка |
| --- | --- | --- |
| CultivationRealmDef | id, order, progressRequired, qiMax, nextRealm, breakthroughQiCost, duration | Уникальный порядок, неотрицательные цены, отсутствие циклов |
| CultivationTechniqueDef | id, minRealm, prerequisites, tags, effectKind, effectDef, learnDuration | Ссылки существуют, циклов требований нет |
| CultivationManualDef, после MVP | allowedRealms, pathTags, allowedTechniqueTags, practiceModifiers | Нет невыполнимого маршрута |
| ThingDef свитка | CompProperties с techniqueDef | Ровно один доступный эффект |
| HediffDef состояния | Один HediffComp_Cultivator | Не удаляется из-за severity или естественного лечения |
| HediffDef бонуса | Проверенный stat offset | Один экземпляр на одну активную технику |
| JobDef | Соответствующий JobDriver | Все targets и параметры сериализуемы |

После загрузки Def выполнить проверку каталога: отсутствующие ссылки, отрицательные значения, цены выше максимума Ци, недоступная следующая ступень, неизвестный effectKind. Ошибка перечисляет defName и поле. Невалидное действие отключается; невалидный каталог основной прогрессии блокирует начало пути.

Def конвертируются в простые rules DTO, Core не хранит ссылки на Def. Для нового IronBody-подобного пассива достаточно XML. Новый принцип действия, например перенаправление повреждений на другого Pawn, требует C# и отдельного теста.

## 6. Владелец состояния: HediffComp

Решение MVP: скрытый или явно описанный постоянный Hediff POC_CultivatorState с HediffComp_Cultivator. Он добавляется при команде «Начать путь» и содержит сериализуемое состояние. Не добавлять component каждой пешке через широкий XML-патч и не полагаться на универсальный Pawn comp API без проверки.

CultivatorState содержит realmId, progress, qi, techniqueStates, schemaVersion. После MVP: manualId, instability и структурированные данные FoundationPreparation/FinalFoundation (§15); прежнее условное имя foundation не означает ещё один Realm или параллельное поле качества. SaveData адаптера содержит primitive-поля и коллекции, а Core получает/возвращает модель. Никаких дубликатов состояния в Dictionary<Pawn,...> как втором источнике истины.

CultivationService — единственное место мутаций состояния культивации. UI, Jobs и поздние интеграции отправляют соответствующие команды через него. Будущий SpiritualHealthService (§16) отдельно изменяет духовные повреждения, не Realm/Progress/качество; синхронизация функциональных ограничений выполняется через CultivationService. Он проверяет наличие единственного state hediff, допуск и активную операцию.

Пассивный Hediff POC_IronBodyEffect — производный результат изучения, не самостоятельное знание. ReconcileEffects добавляет отсутствующий эффект и удаляет дубликаты только своих Def. Вызывается после обучения, завершения загрузки и миграции, а не каждый tick. Защита состояния от удаления сторонними модами не обещается; стандартное лечение и возрождение проверить.

Преимущество: состояние путешествует вместе с Pawn при переходе карты/каравана. Это проектное ожидание, обязательно проверить вместе с сохранением off-map Pawn. Смерть не удаляет запись до удаления самой пешки; возврат живой пешки не создаёт второй экземпляр.

## 7. Jobs, UI и эффекты

| Механика | Выбранная точка расширения | Проверить при реализации (§2) |
| --- | --- | --- |
| Меню места | ThingComp с вариантами float menu выбранной пешки | Точная сигнатура CompFloatMenuOptions и выбранный Pawn |
| Окно | Window_Cultivation и базовый оконный стек | Render callbacks и типы rect/цвета через 1.7 references |
| Медитация | Собственный JobDriver и Toils | Pathing, reservation, остановка по needs, отмена |
| Чтение свитка | ThingComp + JobDriver_LearnTechnique | Стопки, Destroy/Consume, повторное обучение |
| Прорыв | JobDriver_Breakthrough | Продолжение Job после save, атомарность завершения |
| Пассив | Hediff со stat offset | Реальное имя StatDef, единицы и складывание |
| Активные техники, позднее | AbilityDef/AbilityComp адаптер | Доступность без Royalty и структура Ability 1.7 |
| Поздние NPC | Узкая точка генерации Pawn | Vanilla hook или минимальный Harmony-патч |

MVP использует Window, а не обязательную отдельную ITab. Кнопка открытия окна доступна у места практики даже до получения state. Это снижает число интеграционных точек. Полноценную вкладку пешки добавить после исследования.

Выдача команд стандартным интерфейсом Jobs без бессрочного playerForced поведения. Каждая команда повторно проверяет условия после UI и перед итоговой мутацией.

Медитация считает только ticks реально выполненного toil. Delta считается одной операцией для Progress и Qi, caps применяются независимо. Не сканировать все карты/пешки, не начислять за время загрузки. State не нуждается в постоянном ticking для MVP.

BreakthroughService применяет результат ровно один раз. MVP без RNG, без расходов на старте: повторная проверка → единая мутация Realm/Progress/Qi → обновление эффектов → уведомление. До финального шага Job не изменяет ресурсы. Сохранение обрабатывается на том же игровом потоке, в середине последовательности мутации yield не допускается. Идемпотентность дополнительно обеспечивается проверкой ожидаемой исходной ступени.

Учение: подтверждение доступности → резервирование свитка → чтение → финальная проверка → добавление знания и расход одного экземпляра → ReconcileEffects. Учёт награды и расхода должен завершаться в одной фазе без yield; восстановление прерванного Job не выдаёт два бонуса.

## 8. Сохранения и миграции

Сериализация адаптера через проверенные Scribe API. Плоские значения — Scribe_Values; списки состояний техник — Scribe_Collections с корректным режимом deep; реальные ссылки на пешек у будущего наставничества — Scribe_References. Точные перегрузки и lifecycle проверяются на game DLL.

Сохраняются schemaVersion=1, строковые realmId/techniqueId, progress, qi, mastery, активность техники. Строковые ID позволяют сохранить неизвестное знание после отключения content-пакета. Не сериализовать enum ordinal, C# type name в качестве идентификатора ступени, индекс DefDatabase или статические caches.

После загрузки:
1. Прочитать старую версию и выполнить последовательные миграции DTO.
2. Нормализовать отрицательные/NaN/Infinity значения и caps.
3. Разрешить ID через текущий каталог и alias map.
4. Неизвестные техники сохранить неактивными с одним предупреждением.
5. Неизвестную ступень сохранить как исходный ID, заблокировать практики и предложить документированное восстановление; не сбрасывать тихо в I.
6. Только после разрешения ссылок пересобрать caches и производные эффекты.

Если schemaVersion выше поддерживаемой, заблокировать изменения этого состояния и выдать предупреждение; downgrade не обещается. Полную lossless round-trip неизвестных будущих полей не гарантировать.

Для каждой миграции — fixture DTO/save и expected result. Тесты: начальная версия, промежуточная версия, отсутствующее поле, неизвестный content ID, повторный запуск мигратора. До public 0.1 release подготовить baseline save; не переименовывать поля без migration.

Установка в существующий save проектируется через явный вход колониста: не нужна массовая миграция всех Pawn. Удаление мода с save не объявлять безопасным; Jobs, Hediffs и предметы остаются ссылками на мод. Перед обновлением хранить резервную копию.

## 9. DLC как отдельные пакеты

База не требует Royalty, Ideology, Biotech или Anomaly, не ссылается на их Def и не регистрирует их контент.

Каждая integration поставляется отдельным mod root с собственной metadata, dependency на базу и соответствующий DLC. XML и DLL грузятся только при активном пакете; механизм dependency/load-order проверяется на 1.7. Простая проверка «DLC активно» внутри метода не защищает от ошибки разрешения типа при загрузке assembly.

Контракты базы — конкретные policy DTO и ограниченные адаптерные интерфейсы, например CultivationPolicyProvider; добавлять их при появлении первой интеграции, не строить универсальную plugin-систему в MVP. Без интеграции используется neutral policy.

Ideology меняет policies и ritual hooks; Royalty добавляет взаимодействие с псионикой; Biotech — gene/age adapter; Anomaly — источники нестабильности. Состояние основных ступеней и техник всегда принадлежит базе.

Отключение integration: сохранённые ID неизвестного дополнительного контента остаются dormant; базовая прогрессия продолжается, если она не зависит от этого ID. Не обещать удаления всех DLC без последствий для vanilla save.

Матрица проверок: Core только; Core+каждый отдельный DLC; все DLC; база+integration+нужный DLC; база с DLC без integration; integration без DLC должен быть недоступен в менеджере/явно диагностирован. Комбинированные интеграции тестируются до их выпуска, не в 0.1.0.

## 10. Harmony и совместимость

Цель MVP — ноль Harmony-патчей. Пользовательское окно, предметы, Jobs и Hediffs должны обеспечивать цикл без перехвата общего тика, урона и generation.

Если понадобится патч: описать отсутствие обычной extension point, проверить метод и аргументы на текущем build, предпочесть узкий postfix/prefix, включать только нужный модуль. Transpiler — крайний вариант с отдельным временем на поддержку. Ошибка поиска patch target отключает интеграцию с явной диагностикой и не ломает основной цикл.

Не использовать Prepatcher и не патчить private engine internals ради ранней оптимизации. Совместимость с другими культивационными модами не заявляется: одинаковые бонусы могут складываться и портить баланс. Multiplayer — отдельная разработка.

## 11. Сборка, DLL и Docker

SDK-style сборка библиотеки, детерминированные параметры, точные references по RimWorldReferencePath. Private=false для игровых assemblies: они не копируются в mod/Assemblies. Не подключать весь каталог wildcard. Дополнительные managed references добавлять только по конкретной compile error и metadata.

Core.dll включается в релиз вместе с адаптером; test DLL, игровые DLL, Harmony, SDK, refs, NuGet cache, secrets, saves и исходный decompiled game code не включаются. Packaging проверяет allowlist. dotnet build, не self-contained publish и не NativeAOT.

Docker подходит для managed-сборки и тестов Core на Linux. Это не проверка загрузки Windows-игрой и не headless игровой тест. Нативные engine DLL не запускать в контейнере.

Предлагаются два режима:
- **Offline build:** .NET 10 SDK, заранее подготовленный package cache, read-only refs, сеть none; build --no-restore после отдельного restore.
- **Agent:** тот же build toolchain и закреплённый Codex CLI; egress только через контролируемый proxy к разрешённым OpenAI endpoint. Без MCP.

Контейнер: non-root UID, cap-drop=ALL, no-new-privileges, read-only root, tmpfs для временных каталогов, writable только repo и необходимые caches, CPU/RAM/pids limits. Нет docker.sock, host network, privileged, SSH agent и доступа к домашнему каталогу Windows. Только отдельные refs read-only. Права Docker не гарантируют секретность ключа от процесса того же пользователя.

Allowlist сети — внешняя настройка firewall/proxy; обычная bridge-сеть Docker сама её не создаёт. Если proxy ограничение не работает, использовать offline-сборку и ручную подготовку запросов либо наладить proxy до автономного agent mode. Network none несовместима с живыми API-запросами из этого же контейнера.

Restore/download происходит отдельным ограниченным шагом без API-ключа; после подготовки runtime image и NuGet cache можно работать без NuGet-доступа. Не зашивать игровые DLL/ключ в image. Build-manifest: image digest, SDK, CLI version, game build, hashes references, packages lock, commit.

## 12. Проверки и выпуск

Автотесты Core: cap Progress/Qi, нулевой delta, разные размеры delta за одинаковое время, прерванный/повторный прорыв, duplicate learning, migration. XML: well-formed, уникальные POC_ IDs и связность. Игра: загрузка, меню, pathing, потребности, чтение, бонус, прорыв, save/reload, off-map и новый запуск.

Обновление unstable: отметить новый build, пересобрать с его DLL, запустить smoke matrix и старый baseline save. При несовместимости не перезаписывать рабочие save; прежние refs оставлять приватным snapshot. Стабильная 1.7 получает отдельный compatibility report; одинаковый major/minor номер не заменяет проверку.

Нет доступа к локальному Steam и Docker пользователя в этой сессии. Ни запуск игры, ни компиляция мода не проводились. Перечень закрываемых экспериментов находится в [RESEARCH.md](RESEARCH.md).

## 13. Расширение на животных: минимальная архитектура

### 13.1. Сохранить существующий owner

CultivatorState, CultivatorSaveData, CultivationService и HediffComp_Cultivator остаются общими для допущенных Pawn. Не создавать AnimalCultivatorState, отдельный BeastProgress или второй authoritative словарь. Значительная переработка MVP не требуется: достаточно оставить Core независимым от колониста и вынести человеческий допуск к командам из математических правил.

В 0.1.0 действует единственная человеческая политика из GDD §3. Не добавлять животным Hediff, новые поля, тики, Def или animal UI «для готовности». В 0.4.1 вводится небольшой CultivationEligibilityRules в адаптере с проверкой вида, зрелости и поддержанного health-контекста, затем отдельной проверкой конкретного действия. CanHoldCultivation и CanPerformAction — предлагаемые методы нашего адаптера, не vanilla API. Первое отвечает за возможность носить состояние, второе — за текущую практику/команду. Потеря фракции, сознания или прирученности блокирует действие, но не удаляет знания и ступень.

| Общее | Человек | Животное после 0.4.0 |
| --- | --- | --- |
| State, caps, transition, migration | Human action eligibility | Animal action eligibility и профиль вида |
| CultivationService, idempotent result | Meditate/Learn/Breakthrough Jobs | Редкое пассивное обновление, своё ожидание прорыва |
| Def каталог и reconciliation | Руководства и свитки | Врождённый пассив, поздние особенности |
| Read-only state snapshot | Window_Cultivation у места | Отдельный компактный animal presenter у выбранной пешки |

Проверки и DTO дополняются по мере нужды; наследование HumanCultivator/BeastCultivator, DI и универсальный AI framework не нужны. Имена собственных классов здесь — проектные предложения.

### 13.2. Допуск видов и контент

В 0.4.1 достаточно одного CultivationSpeciesProfileDef с явными ссылками на 2–3 проверенных вида, множителями практики, допустимыми Realm и innate effect ID. Общие Realm I/II используются без копии лестницы; профиль задаёт способ практики и ограничения. Впоследствии ветвь может ссылаться на дополнительные RealmDef, сохраняя тот же алгоритм. Не сравнивать «силу ранга» разных ветвей только по порядковому номеру.

Явный запрет имеет приоритет над профилем; конфликт нескольких разрешающих профилей диагностируется, произвольный первый профиль не выбирается. Для неподдержанного вида пробуждение недоступно. Существующее состояние при исчезнувшем профиле сохраняется, прогресс и специфические эффекты приостанавливаются с объяснением. Для исчезнувшего самого race Def безопасная загрузка не гарантируется: это ограничение сохранения игры, а не только нашего state.

Модовое животное подключается opt-in профилем без изменения базового класса и без широкой вставки comps во все race Def. Одних Animal/Humanlike-флагов недостаточно для заявления совместимости. Проверить здоровье, зрелость, needs, тело, обучение, stats и сторонние эффекты. Механоиды, сущности и специальные расы по умолчанию не допускаются. Требующие части тела эффекты проверяют наличие частей и не считают структуру человека универсальной.

Innate traits используют общий эффектный адаптер, но отдельный источник идентичности от techniqueId: зверю не записывается изученный человеческий IronBody. При выпуске добавить только необходимые поля через последовательную миграцию; schemaVersion=1 и имена save-полей MVP сейчас не меняются.

### 13.3. Редкое обновление и время

AnimalCultivationUpdater вводится только с 0.4.1. Предпочтение — проверенный интервальный callback существующего HediffComp: тяжёлые расчёты примерно раз в 250 игровых ticks с распределением по Pawn ID. Фактические CompPostTick/CompPostTickInterval и их delta не подтверждены для установленной 1.7; точку выбрать после Q20. Нельзя предполагать, что TickRare сработает у произвольного Pawn. Если доступен лишь tick callback, выполнять только дешёвую проверку срока до следующего обновления.

Минимальный fallback при проблемах callback — один MapComponent со списком только активных зверей и ограниченным числом записей на обновление. Список является восстанавливаемым индексом, не владельцем state; регистрация/снятие при spawn/despawn и одно восстановление после load проверяются. Такой менеджер добавлять только по результату профилирования, не вместе с первым вариантом.

Не обходить все Pawn карт или мира каждый tick и не создавать state обычным животным. Коэффициент среды кэшируется на короткий интервал либо обновляется при движении/смене зоны; сканирование всех источников на каждое животное запрещено. Для первого среза хватает фиксированных условий без духовной карты биома. Учитывать время разрешённой практики, а не слепое currentTick−lastTick: сон/бой/голод между выборками не должны начислять произвольный длинный delta. Допускается погрешность не больше одного выбранного интервала на границу условия, измеренная в тесте; дневной лимит делит delta на границе суток.

Сохранять использованный суточный бюджет и день его применения; на load восстановить их, сбросить непроверенный elapsed interval. В караване, контейнере, криптосне, вне карты, при смерти и на паузе роста нет; при возвращении часы не догоняются. Переход/стоимость применяется на игровом потоке одной командой сервиса с проверкой ожидаемой Realm. Незавершённое ожидание звериного прорыва в первом срезе безопасно отменяется без затрат/награды.

### 13.4. Lifecycle и сохранение

HediffComp хранится на самом Pawn независимо от wild/tamed и не переносится между таблицами при приручении. Нельзя удерживать всех диких Pawn сильными ссылками ради прогресса или запрещать движку удалять их. Состояние сохраняется только пока сама пешка удерживается и сериализуется игрой. Permanently discarded Pawn не восстанавливается из нашего глобального реестра.

| Событие | Ожидаемая семантика / необходимая проверка |
| --- | --- |
| Приручение, одичание, смена владельца | Тот же owner, Realm/Progress/Qi; новая проверка доступных действий |
| Despawn → караван → spawn | Round-trip значений, отмена ожидания, no catch-up |
| WorldPawn/mothball, временная выгрузка карты | Сохранение при retained Pawn; без предотвращения mothball ради роста |
| Смерть/труп/возрождение | Нет роста и второго state/effect; возвращённый Pawn сверяет производные бонусы |
| Продажа/передача | Состояние следует Pawn; чужая фракция не оставляет player controls |
| Исчезновение профиля | Dormant специфический контент, сохранённые исходные ID, одно предупреждение |
| Удаление самого Pawn игрой | Никакого нового владельца state; убрать из runtime индекса |

Договоры позже используют разрешаемые Pawn references с null-safe разрывом. Ядра требуют отдельной сохранённой записи однократной выдачи и определённой политики resurrection; проверить где хранить маркер при удалении трупа и модовом воссоздании Pawn. Не обещать защиту от всех сторонних клонеров. Эти поля и ссылки не создаются в MVP или 0.4.1.

### 13.5. Gate SB0 и приёмка 0.4.1

После завершения 0.4.0 проверить Q18–Q23 и Q26–Q27 из RESEARCH, затем отдельный build/load spike. SB0 не является условием выпуска 0.1.0. Человеческие Jobs и UI не считаются подходящими животным без эксперимента. Человеческий интерфейс места продолжает отвергать животных; animal presenter показывает состояние, источник пассива, блокировки и общую политику без кнопок чтения/ручной медитации.

Приёмка: один вызов пробуждения → один state; пассивный рост и caps по GDD §13; один прорыв/пассив; сохранённый дневной лимит; 10 reload; переходы карты/каравана/прирученности; животное без rest need получает безопасный отказ. После обновления старые человеческие saves проходят прежний baseline. Core тестирует caps/переход/лимит, игра — здоровье, UI и AI. Базовый запуск без DLC обязателен.

Профиль нагрузки: одинаковые saves с 100 и 500 животными, отдельно 0/10/50 пробуждённых; записать hardware/build/mod list, TPS, время обновления и allocations относительно той же сцены без animal feature. Начальный gate — не более 5% медианной потери TPS и отсутствие роста удержанных Pawn после серии spawn/despawn; это проектный порог, не измеренный результат. Повторить при существенном шуме. Если gate не пройден, сократить частоту/перечень средовых расчётов или отложить animal release. Изменение глобального тика/AI патчем не является первым решением.

## 14. Ambient Qi: независимое состояние карты

### 14.1. Минимальное расширение и граница MVP

Существующие CultivatorState / HediffComp_Cultivator не становятся картой энергии. Поле qi остаётся Personal Qi, schemaVersion=1 MVP не меняется ради проекта будущих данных. В 0.4.2 вводится самостоятельный MapComponent_AmbientQi — предлагаемый класс нашего адаптера, с собственной ambientSchemaVersion. Он владеет источниками/подавителями и позже резервами. Расчёты геометрии, density composition и воздействия по snapshot — чистые функции Core без Verse/Def/Pawn. Имена типов ниже — проектные, не свидетельство существования API 1.7.

CultivationService в версии с Ambient Qi получает AmbientQiSample для конкретной разрешённой практики; sample содержит D, используемый уровень, revision и фактор среды. При отсутствии системы/источников sample нейтральный: D=0, множители 1, ambientSupport=0. Никаких поисков карты из Core и резервных личных qi-словарей. Человеческие Jobs и AnimalCultivationUpdater по-прежнему определяют, когда разрешено начисление; окружение не создаёт свой второй таймер прогресса. Создавать это API, DTO и MapComponent в 0.1.0 запрещено scope.

Отдельный EnvironmentalExposureService обрабатывает поддержанных живых пешек, включая обычных без CultivatorState. Длительная Spiritual Strain сохраняется у самой пешки через собственный HediffComp_SpiritualStrain; создаётся только при S>0, удаляется после полного восстановления. Это иной тип воздействия, а не дубль progress/qi или Instability. Он не добавляет пешке культиваторский state и не удаляет другие Hediffs. Переносимость берётся из существующего Realm, если он есть, иначе из базового профиля. A/V исходно вычисляются из профиля с default=1; persistent override добавляется лишь при реально сохраняемой индивидуальной особенности.

### 14.2. Сравнение пространственного хранения

| Подход | Цена / свойства | Решение |
| --- | --- | --- |
| Список аналитических кругов (центр/радиус/D) | Память O(Z), точный запрос O(Z); не нужны данные каждой клетки | Выбрать для 0.4.2 с небольшим собственным bucket index |
| Список произвольных клеток / vanilla Area | Удобное рисование, но память зависит от площади, отдельные lifecycle/overlay hooks | Не нужно для первого среза; нельзя предполагать Area API для поля |
| Полная scalar grid | O(N) память, O(1) lookup; сериализация и обновление по клеткам | Только при доказанной нужде; не наполнять все клетки каждый tick |
| Sparse/chunk grid | Эффективна для локальных изменяемых полей, но сложнее frontier и миграции | Кандидат отдельной клеточной симуляции после 1.0 |
| Vanilla pollution grid/обёртка Biotech | Доступность без DLC, тип значения, hooks и визуализация неизвестны для build 1.7 | Не использовать для хранения или исполнения Ambient Qi; исследовать только как аналог |

Для оценки, не измерения runtime: один float32 на клетку даёт около 244 KiB на 250×250, 625 KiB на 400×400 и 977 KiB на 500×500; три таких слоя на 500×500 — около 2.86 MiB до объектов, overlay, save и GC. Небольшой массив сам по себе не проблема, но его многократный пересчёт для всех пешек и кадров — проблема сложности. Список зон избегает клеточных мутаций, full-grid diffusion не оправдана первой игровой задачей.

Первичный пример локальных зон найден в авторском MapComponent_PsycastsManager проекта Vanilla Psycasts Expanded, каталог **1.6**: список зон с центром/радиусом и отдельной сериализацией [RESEARCH S21]. Это пример структуры, не доказательство доступности API 1.7, производительности подхода или независимости VPE от DLC. Код не копируется, зависимость VPE/VEF не добавляется. Официальное описание Biotech [S20] подтверждает игровой аналог, но не публикует контракт pollutionGrid.

### 14.3. Записи, профиль и запросы

| Данные | Минимальный состав / владелец |
| --- | --- |
| AmbientQiMapData | ambientSchemaVersion, generationInitialized, sourceRecords, nextSourceId; карта |
| AmbientQiSourceRecord | stable sourceId, kindDefId, center x/z, radius, density, enabled, optional bound Thing reference; карта |
| Suppressor record | sourceId, геометрия, capDensity, режим; фактическую работоспособность проверяет адаптер питания |
| AmbientQiSourceDef | Вид записи, defaults, радиус/плотность/лимиты; декларативные данные |
| AmbientQiSample | D, band, environmentRevision; transient, для текущего запроса |
| SpiritualStrainSaveData | exposureSchemaVersion, S и нужные overrides; только на Pawn |
| Производные данные | Bucket index, active source status, actor queue, samples и overlay cache; не сериализуются как владельцы |

Source records — единственный owner динамических параметров поля. ThingComp источника/подавителя хранит только связь sourceId и посылает команды карте; не ведёт второй резерв/таймер/плотность. Неподвижные природные записи привязаны к карте; их видимый marker — производное представление. Для здания bound reference сверяется после load: отсутствующий/уничтоженный объект выключает запись, а не оставляет невидимую ауру. Передвижение, despawn, смена карты и установка нового здания регистрируются идемпотентно; переносу резервов в будущем нужна отдельная транзакция.

Геометрия круглая по расстоянию между клетками в x/z, граница включительна; выход за карту отсекается. Не обходить клетки круга при каждом запросе. Итог D — max эмиттеров, затем min caps подавителей по GDD §14.3, с clamp [0,100]. Ошибочные NaN/отрицательные радиусы, неизвестный вид и duplicate sourceId диагностируются; неизвестная запись сохраняется dormant. Явный запрет/конфликт профилей не выбирает случайную обработку.

Первичный index — словарь buckets 16×16 клеток с ID кругов, чьи bounding boxes их пересекают. Query смотрит кандидатов bucket и точное расстояние; плотность не интерполируется из чужой клетки. Это O(k) на запрос, где k — локальные кандидаты; худший случай остаётся O(Z). Большие/перекрывающиеся радиусы и сотни источников требуют стресс-теста и ограничения контента, а не обещания O(1). Полного сетевого графа, quadtree и публичного plugin SDK не нужно.

При изменении/перемещении/активации источника invalidation затрагивает старые и новые buckets; увеличивается environmentRevision. На первом этапе допустима общая revision карты для actor cache, но не rebuild всех клеток. Actor sample cache действителен только для той же карты, точной позиции, revision и короткого интервала; движение внутри bucket не должно сохранять старый результат. Для финальной операции прорыва запрашивать актуальный sample после проверки работоспособности источников, а не доверять GUI cache.

### 14.4. Обновление, exposure и overlay

MapComponent имеет только дешёвую проверку расписания на каждом tick; точные callbacks, автоматическое создание и lifecycle проверить на AQ0. Рекомендуемое окно — 250 игровых ticks, разнесённое по карте/ID. Построить snapshot поддержанных spawned Pawn раз в окно и обрабатывать ограниченную порцию очереди по ходу следующих ticks; каждый актор получает не более одного интервала работы за окно. Это обход O(P) **за окно**, не всех карт/мира каждый tick. Actor queue — временный индекс без ownership; dead/despawn/transfer удаляются, ссылок на WorldPawn за пределами карты не удерживать. Если проверенные notifications позволяют поддерживать список без обхода, использовать их; не вводить Harmony только ради этого.

Для 0 источников не опрашивать здоровых пешек: остаётся только восстановление уже имеющейся S у spawned Pawn. После загрузки/смены карты нет начисления currentTick−последний сохранённый tick. S заморожена вне карты/в контейнере; после возврата начинается новый подтверждённый интервал. При отключении всей Ambient-системы через будущую настройку полезные множители становятся нейтральными, а существующая S безопасно убывает на карте; не оставлять вечный debuff.

Практика использует собственный actual-toil delta, exposure — отдельный exposure delta: одни часы не начисляются дважды. Для S использовать проверенную константу ticks/час, clamp и правило GDD §14.2. При изменении плотности/движении погрешность выборки ограничить одним окном (250 ticks) на границу, не накоплением произвольного пропущенного времени. Такой предел надо измерить; если нельзя обеспечить, хранить краткую историю переходов в текущем окне либо уменьшить его, не делать слепой catch-up. Улучшение/ухудшение источника обновляет revision сразу при доступном notification; если состояние питания опрашивается, документировать задержку не более окна и перепроверять его перед итоговыми командами.

Effects обновляются при смене severity band S, а не каждый tick. Один свой Strain Hediff с проверенными стадиями stats/thought; Scribe хранит S, derived эффекты не дублируются. Exposure не требует разрешения на культивацию: обычный человек может страдать, сохраняя отсутствие CultivatorState. Животное получает только подходящие эффекты без человеческого mood tracker. Неподдержанный вид исключается с объяснимым ограничением. Изменение генов/модового профиля инвалидирует A/V/T cache, не создаёт ранг.

Overlay 0.4.2 рисует контуры/полупрозрачные границы видимых кругов только при включённом режиме; общий mesh/cache перестраивается при revision, не каждый кадр. В пересечении контуры — ориентир, точный цвет/число в выбранной клетке показывает итог query с подавлением. Не генерировать полную текстуру карты и не опрашивать всех Pawn из draw callback. Ограничить число предупреждений: одно об изменении источника/достижении severity band, без спама по каждой выборке. Для уведомления риска при переключении допустим один ограниченный обзор текущих зданий/пешек по событию, не на каждом update.

### 14.5. Сохранение, генерация и миграции

Карта сериализует records и собственную версию через подтверждённые Scribe API. Координаты сохраняются как x/z, sourceId/Def IDs стабильны; размеры карты берутся из контекста, records валидируются на bounds. Источники новой карты создаются один раз с generationInitialized и детерминированным сохранённым результатом; нельзя повторять генерацию в FinalizeInit при каждом load. GenStep/MapGenerated или эквивалент проверяются в Q33, не считаются готовым контрактом.

**Старый save без Ambient данных → пустой список, initialized=true, D=0.** Нельзя считать отсутствие секции основанием случайно создать опасные жилы под колонией. Различие новой карты и старого save фиксируется надёжным lifecycle hook; если различить нельзя, безопасный fallback — без автогенерации, добровольное событие с одним источником. Это минимальная альтернатива, не обязательное изменение выбранной геометрии.

После load: прочитать версию → миграция records → нормализация → разрешение Thing/Def references → один rebuild индекса/визуализации → проверка актуальной работы зданий → восстановление actor queue без исторического delta. Последовательные этапы выполнять после подтверждённого разрешения ссылок. Поздний schema резервов мигрирует отдельно; не менять schema культиватора ради сетки. Слишком новая версия ambient блокирует её мутации с предупреждением; безусловное обнуление неизвестных records не допускается.

Spiritual Strain следует за Pawn при переходе карты/каравана; суточный лимит животного остаётся в прежнем владельце. Ambient-плотность не сериализуется у каждой пешки. В позднем прорыве отдельно сохраняются минимум среды за подготовку, параметры попытки и уже выбранный результат; изменение поля не вызывает повторный RNG. Новые поля вводятся только в выпуске 0.4.2 с migration для уже существующих попыток: нейтральный вклад среды, прежний сохранённый исход. Удаление модификации/пакета среды не объявляется безопасным для save с её Hediffs/зданиями.

### 14.7. Резервы и будущая клеточная модель

0.6.2 может добавить reservoir к тому же source record: capacity, charge, recharge, operational mode и единую историю изъятий интервала. Для исследования клеточной модели после 1.0 сохранить контракт чтения density, заменить только пространственного владельца/вычислитель с явной migration. Аналитические источники могут стать граничными условиями; нельзя суммировать старую ауру и уже накопленное ею поле второй раз. Начать с одного scalar layer и фиксированного dt, dirty chunks/frontier и лимита cells/frame; стабилизация/потери/overflow и одинаковый результат при разном размере update batches — обязательные эксперименты. PollutionGrid допускается изучать read-only на собственной игре, но не вызывать из базы и не делить её save-layer с Ambient Qi.

### 14.8. AQ0, проверки и производительность

До 0.4.2 закрыть AQ0: Q32–Q39 и Q42 из RESEARCH. Ни один пункт не переносится в T0/B00–B09. Pure tests покрывают границы кругов/карты/плотности, max/min композицию независимо от порядка records, отсутствие источников, A/V/T/S, delta partition, caps и однократную мутацию прорыва. Stateful tests покрывают reindex после move/remove/power, отсутствующие references, старый save → D=0, повторную migration, load без regeneration. Игровые тесты необходимы для питания, UI, мыслей/здоровья, Jobs и животных; нет игры — pending.

Числовые контрольные примеры: источники D=50 и 70 дают 70; подавители cap=40 и 20 дают 20; D=0 даёт прежние rates; человек без state при D=60 за 2/6 часов имеет S=0.24/0.72 с допуском одного окна; A=1,V=1,T=60 при D=50 даёт ×1.15 Progress и ×1.25 Qi без роста S; выход в безопасную среду уменьшает S на 0.10/час. У зверя cap 4 часа и state остаются прежними; фиксированный исход поздней попытки после load не меняется.

Матрица: карты 250×250, 400×400 и 500×500, если их поддерживает проверенный build; 0/10/100 пересекающихся зон; 20/100 людей; 100/500 животных, из них 0/10/50 культивирующих; две одновременные карты, overlay on/off, частые power toggles и серия spawn/despawn. Для больших стресс-наборов сначала отдельные оси, затем одна наиболее тяжёлая поддерживаемая комбинация. Записать hardware/build, mod list, TPS, median/p95 затрат update, query counts, allocations, save size/load time и retained Pawn. Не обещать работу больших модовых карт по оценке памяти.

Начальный целевой gate: не более 5% медианной потери TPS от Ambient Qi относительно **того же save со Spirit Beasts, но без Ambient updates**, и не более 8% общей потери двух расширений относительно базы; без накопления Pawn/references и без заметного регулярного кадра полной пересборки. Эти числа — проектные цели, не результаты измерений. Пауза/1x/3x сохраняют семантику игрового времени. Если gate не пройден, ограничить радиусы/число источников, убрать дополнительные средовые запросы, упростить overlay или перенести выпуск; не отказываться от сохранений/защиты от дублей.

Минимальный запасной вариант — один круг, прямой проход по небольшому числу sources при запросе, без bucket оптимизации, если профиль подтвердит достаточность. Данные/Scribe и physics max/min те же. Если невозможно сделать надёжное воздействие без широких AI/health patches, оставить эксперимент вне public release до решения, не выпускать скрытую несовместимость.

## 15. Foundation Quality: данные и переходы после MVP

### 15.1. Минимальные компоненты и единый owner

CultivatorState остаётся моделью Core; HediffComp_Cultivator — единственным persistent owner адаптера; CultivationService — единственным путём мутаций. Не создавать отдельный health Hediff или Dictionary для основания. Schema MVP не меняется в предпроектном этапе. При реализации 0.4.0 вводится ровно необходимое расширение DTO с миграцией от реально выпущенной предыдущей schema, без обещания заранее известного следующего номера.

| Предлагаемые данные | Назначение / правило |
| --- | --- |
| foundationStatus | Unprepared / Preparing / Formed / LegacyProtected; состояния нашей модели, не API игры |
| firstTrainingBiologicalAge, ageHistoryKnown | История первого доказанного часа, unknown разрешён; не единственный аргумент качества |
| FoundationPreparation | trainingHours, plasticityIntegral, sums A/M/N/B/E; текущий ограниченный набор H=120, версия профиля/правил |
| earnedPlasticity | Зафиксированный возрастной вклад после первых полных H; до этого вычисляется из integral/H, не отдельная редактируемая копия |
| acceptedPreparation | Один лучший целый завершённый snapshot не-возрастных сумм, H, связанный P/profile и preparationRevision; Q прогноза вычисляется, не является вторым authoritative полем |
| replacementPreparation | Только при реально начатой переподготовке: новое ограниченное окно; старый accepted не меняется до commit |
| FinalFoundation | Необязательный immutable snapshot Q, categoryId и qualityPolicyVersion; создаётся атомарно только при успешной Formation или явном улучшении |

| Formation attempt | Расширение прежней записи попытки: preparationRevision, Q/category policy snapshot, token, phase, result, costApplied; не второй parallel attempt |
| reinforcementState, позднее | Program revision/checkpoint, paid Qi, consumed flag; только при выпуске укрепления, не заглушка в 0.4.0 |

Суммы ограничены количеством факторов, не растут с числом занятий. После принятия нового лучшего snapshot ненужное старое окно удаляется; не хранить историю всех наставников/книг/клеток. Знания и proficiency не копируются в preparation: сохраняются доказанные агрегаты, а текущая доступность чтения/прорыва проверяется адаптером.

Qi Affinity берётся из одного существующего профильного/индивидуального источника (§14), не создаётся «foundationAffinity». В 0.4.0 профиль с default=1 работает без MapComponent; 0.4.2 использует тот же контракт. Meridian Plasticity — чистая функция биологического возраста и выбранного age profile, не постоянно тикающий ресурс. Данные B — нормированный snapshot пригодности, Instability/Strain остаются у прежних владельцев. Не начислять дублирующий Progress за quality hours. Пока Formation pending, новые часы/замена accepted snapshot заблокированы; начало Formation приостанавливает незавершённую переподготовку. Одна пешка не выполняет две программы одновременно.

### 15.2. Core и конфигурация Def

Предлагаемые собственные функции/типы: FoundationPreparationState, FoundationQualitySnapshot, FoundationRules.AccruePreparation / PredictQuality / CommitFormation, AgePlasticityRules и дополнение BreakthroughRules.CanAdvance. Они не требуют Verse, Pawn, Scribe, DLC, мирового времени или RNG. Адаптер предоставляет biological age, actual delta и проверенный snapshot; UI читает готовый view model. Не нужен отдельный framework/иерархия Human/AnimalFoundation.

Def-driven данные: CultivationAgeProfileDef (species references, maturity/action policy, age→P curve), FoundationQualityPolicyDef (H, веса/нормализация, categories и ceiling rank IDs), Manual foundationSupport, учебная компетентность наставника и доступность его метода. Категории имеют stable string IDs, minScore и maxRealmId; ordinal enum не сериализуется. Q и P вычисляются в double с одной согласованной политикой округления; threshold сравнивается до отображения в UI, 59.999 не становится 60.

Каталог потолков содержит **символические rank IDs** полной лестницы, включая Transcendence/Immortal, отдельно от реально загружаемых RealmDef. Отсутствие ещё не выпущенного RealmDef не требует создавать фиктивный игровой контент: policy знает планируемый потолок, а availability gate запрещает переход. Неизвестный ID вне объявленной лестницы — ошибка; ссылка на отсутствующую уже поддерживаемую ступень — ошибка каталога. Для расширяемых ветвей требуется явное отношение допустимых рангов, не сравнение случайных ordinal разных путей.

Валидатор проверяет: монотонные уникальные thresholds, полный диапазон Q, отсутствие перекрытий, неотрицательные веса и H>0; возрастные кривые с определённым взрослым fallback и finite values; однозначный профиль вида; Weak ceiling=QiGathering, Ordinary допускает POC_Foundation; Flawless включает путь через Transcendence; нет несуществующих required Manuals/mentor method. Несогласованная конфигурация блокирует конкретные будущие операции с диагностикой, не удаляет накопленное состояние. Потолок и текущая доступность ранга проверяются независимо.

### 15.3. Учёт времени и прогноз

Подготовка обновляется только существующим actual-toil callback подходящего занятия и новой явной подготовительной программой 0.4.0 при необходимости продолжить занятия с полными caps. Не опрашивать всех Pawn каждый tick и не вводить второй таймер. Hour delta переводится проверенной константой, обрезается до остатка H; лишние ticks не копируются автоматически в следующее окно. Каждый завершённый интервал засчитывается ровно один раз. В возрасте перехода через границу профиля интеграл делится по проверенной истории/доступной интерполяции, либо используется малый интервал с документированным допуском; год при последнем прорыве не заменяет всю историю.

Первые 120 часов копят plasticityIntegral вместе с обычными агрегатами. Исторический P фиксируется лишь после полного объёма. Для частичного окна все contributions считаются с denominator H: нельзя получить полный возрастной бонус за первый час. firstTrainingBiologicalAge сохраняется после первого часа, но не управляет earnedPlasticity напрямую. Переподготовка сохраняет только заработанный P, заново усредняет A/M/N/B/E полного нового окна и принимает его целиком, только если итог лучше. Snapshot revision меняется только после реального улучшения/явного подтверждённого изменения правил, не от открытия окна.

Менторский/ambient множитель роста Progress не меняет длительность preparation delta. Одна пара наставник/ученик на час, без multi-mentor stacking. Ambient provider до 0.4.2 neutral E=0; после появления среды historical E учитывается только за новые подтверждённые занятия. У уже сформированного основания ни появление жилы, ни новый возраст не меняют Q. У готового старого окна E остаётся 0; желающий использовать лучшую среду проходит полное новое окно.

Кэш прогноза производный: invalidation после accrual/commit/migration/завершения нового окна. Текущие здоровье/Instability/action eligibility для пуска операции проверяются заново, исторические баллы не переписываются незаметно. Core тестирует зависимость итогов от разбиения времени; transient кеши не сериализуются как второй источник.

### 15.4. Gate до вероятности и транзакция

Последовательность BreakthroughRules: resolve доступные Def/ранги → проверить species/action/current/target → готовность окна для Formation → определить прогноз или FinalFoundation ceiling → проверить target≤ceiling → обычные Progress/Qi/health/Manual/подготовка → **только тогда** оценить p. Недопуск возвращает typed blocked reason, а не вероятность 0.10. Прежний детерминированный I→II не требует FoundationPreparation и не меняется.

Сервис одной командой создаёт прежнюю pending attempt со snapshot выбранного acceptedPreparation, token и policy version. Token генерируется один раз игровым адаптером и сериализуется, Core не вызывает Rand. Существующий механизм завершительной фазы вычисляет исход из сохранённого token и допустимого финального p и сохраняет resolved result; token/result на load не обновляются. После безопасной отмены незавершённая попытка того же snapshot сохраняет token; новый после настоящего failed result требует оплаты/восстановления по Def. Публичный UI не показывает token и ранний исход. Это защита от штатного reload, не от редактирования save/всех сторонних RNG модов.

В финале повторить обычные условия и потолок, затем без yield: committed Realm, личные расходы, immutable FinalFoundation, attempt phase/costApplied → ReconcileEffects. Повторная команда/повторный callback проверяет ожидаемые current Realm, revision и status, не списывает повторно. При сбое rollback в середине одной игровой команды не обещается как DB-транзакция; проверенные exception-free изменения и save lifecycle важны. При неудаче FinalFoundation остаётся null, acceptedPreparation/P сохраняются; failure penalty идёт через прежний сервис. Сам score качества не бросается случайно.

Настоящее снижение Realm при будущем Reforging — отдельная явная операция с подтверждённой ценой/эффектами; migration/обычное aging к ней не приравниваются. Применение техник определяется достигнутым Realm и прежними requirements, не абстрактным будущим ceiling.

### 15.5. Сохранения, миграция и совместимость

Не выводить прошлый возраст начала из текущего биологического, имени, сохранённого Progress или количества прожитых дней. Старая пешка ниже POC_Foundation получает ageHistoryKnown=false, пустую будущую подготовку и **все прежние Realm/Progress/Qi/techniques без изменений**. Новые реальные занятия начнут историю; уже пройденные I→II не повторяются. Подготовка основания доступна на QiGathering с полными caps, поэтому старая пешка не застревает из-за отсутствия учтённых ранее часов.

У старого культиватора на POC_Foundation или выше: foundationStatus=LegacyProtected, FinalFoundation=null, legacyRealmFloorId=фактически достигнутый на момент включения Realm. Не назначать Weak/Flawless и выдуманные 120 часов. Ранг, техники, эффекты и mastery сохраняются. Следующий ещё не достигнутый Realm требует отдельной процедуры **legacy assessment**: та же взрослая 120-часовая программа без отката Realm, по фактически наблюдаемому возрасту и подготовке; её результат фиксируется как новое quality snapshot с сохранением legacy floor. Эта процедура нужна для уже развитых входящих saves, не новая выгодная возможность обычного культиватора менять основание.

Эффективный допуск legacy=max(потолок подтверждённого качества, legacy floor) по той же явной лестнице. Например, старый GoldenCore с оценкой Ordinary остаётся GoldenCore, но NascentSpirit не открывается автоматически; нужны специальные улучшения. Старый Transcendence остаётся там, но не получает бесплатный Immortal только из-за существования категории Flawless. UI честно показывает защищённый достигнутый ранг и неизвестное/оценённое качество. До завершения assessment практики текущего ранга и обучение не блокируются.

При ребалансе category→ceiling/threshold уже фиксированный snapshot не пересчитывается из возраста/нынешнего Manual. Изменения policy версионируются и переводятся явной миграцией; текущий Realm защищён даже если новый cap ниже. Не поддерживать неограниченный каталог всех исторических формул: конкретная известная migration фиксирует необходимый итог. Неизвестные category/policy IDs сохраняются dormant и блокируют будущие мутации основания, а не удаляют state; текущие безопасные знания/эффекты не стираются. Более новая save schema не понижается автоматически.

Поле reinforcementConsumed и будущий special budget принадлежат этому же owner и не обнуляются при смене пути, возрасте, неудаче, смерти/возрождении или переподготовке. Платные checkpoints усилия/ресурсов сериализуются; перенос в список дефектов/сокровищ без owner не допускается. Новые данные, отсутствующие до выпуска конкретного улучшения, получают безопасные defaults, а не автоматическую награду.

### 15.6. DLC, виды и неопределённые API

База 0.4.0 читает биологический возраст взрослой пешки через проверенный адаптер и не ссылается на Biotech learning/growth types. Опциональный детский модуль может расширить action policy только после подтверждения maturity/work/needs. Нет предположения, что Humanlike означает фиксированное lifeExpectancy или обычный human age tracker. Неизвестные профили дают нейтральный возрастной вклад и прежний подтверждённый взрослый допуск; при невозможности определить взрослость сама операция безопасно недоступна, не допускает ребёнка по ошибке.

Biotech child learner обновляет те же preparation sums через сервис; отдельный child potential owner не создаётся. Суточные child caps и ledger вводятся только с этим модулем, фиксируются в persistent state; vat growth/age reversal не начисляют часы. При омоложении уже заработанный P/quality не переписываются; незавершённые первые H учитывают новый фактический biological age только в будущих реально сыгранных занятиях, без reset. Нужны отдельные проверки mods/accelerated aging/gene changes и правила защиты от повторного child allowance по пересечению возрастной границы.

Животные 0.4.1 используют существующую action policy и I→II без human foundation gate. Будущий species foundation profile сможет подать собственный maturity/врождённый вклад в общие DTO, но human Manual/учебный Job не переиспользуется. Для отсутствующего профиля не открывать animal высокие Realm по умолчанию; текущий поддержанный путь не ломается.

### 15.7. Gate FQ0 и проверяемость

FQ0 относится к 0.4.0 после QiGathering/наставничества, не к B00/T0 MVP. До кодирования подтвердить Q45–Q49 из RESEARCH; Q50–Q53 нужны соответствующим поздним расширениям. Unit checks Core: Q boundaries, adult examples, early click, 120h cap, delta partition и несколько возрастов; неудача/дубли, Weak gate до p, Ordinary Formation, Exceptional запрет Transcendence, Flawless без auto-Realm; повторная подготовка не смешивает snapshots, неизвестные ranks/category IDs диагностируются.

State/save matrix: новый взрослый, старый I/II/QiGathering, LegacyProtected Foundation/GoldenCore/Transcendence, неизвестный возраст/профиль, сохранение частичного/полного окна и незавершённой попытки до/после выбора исхода, 10 reload, отмена/failed/успех, dead/resurrected/off-map. Проверять точное сохранение token, одно списание/один результат, absence of retroactive age loss и повторную идемпотентную migration. Настоящие saves прежних выпущенных версий обязательны; DTO тесты не заменяют игровой Scribe round-trip.

Интеграционная матрица: база без DLC/без Ambient; ментор равного Realm с методом и высокий Realm без метода; A/M/N разные; старый добившийся потолка мастер не теряет умения; Ambient neutral/безопасный/перегрузка после 0.4.2; animals I→II по-прежнему независимы; child/vat/age reversal только при выпуске адаптера. Нет массового tick update для quality; профилировать реально активные Jobs и сериализацию агрегатов на нескольких десятках учеников. Если сборка/игра недоступны, результаты pending, не «API подтверждён».

## 16. Spiritual Anatomy: виртуальное здоровье и отдельный sparse owner

### 16.1. Варианты и выбранное направление

| Вариант | Польза | Риски / вывод |
| --- | --- | --- |
| Добавить органы в BodyDef/BodyPartDef | Потенциально привычное дерево стандартного Health | Изменение physical body/health/hit selection, хирургии, death rules, рас/протезов и save references; поведение на 1.7 не подтверждено. Нельзя просто назвать физическую часть «духовной» и считать её независимой |
| Своя virtual anatomy | Профиль/органы развиваются без перестройки physical body, sparse данные обычных людей, контролируемые зависимости | Нужны свои rules, отображение и мост эффектов; цель Health toggle требует отдельного UI исследования |

**Выбрана виртуальная анатомия.** База не добавляет духовные body parts в vanilla BodyDef/BodyPartDef, не перехватывает каждый физический hit и не заменяет штатную медицину. Это архитектурное решение, не утверждение о невозможности физического варианта. Точные health/Scribe/UI hooks проверяются на SA0; публичные примеры старых версий не подтверждают build 1.7.

### 16.2. Владение и структура данных

Один persistent Hediff POC_SpiritualHealth с предлагаемым HediffComp_SpiritualHealth — авторитетный владелец духовных повреждений **для любого поддержанного Pawn**, независимо от культивации. Он создаётся лениво при первом повреждении/сохранении необходимого исторического исключения. Не добавлять HediffComp_Cultivator обычному человеку. Отсутствие POC_SpiritualHealth означает здоровый стандартный профиль, а не отсутствие духовного тела. Это отдельный health-domain owner, не дубликат CultivatorState.

| Предлагаемый тип | Данные / ответственность |
| --- | --- |
| SpiritualAnatomyProfile | Общий шаблон поддержанного вида; базовые/формируемые органы, activation rules и зависимости; runtime DTO без Pawn |
| SpiritualOrganDef | stable organId, функции, activation condition, зависимости, единицы/параметры восстановления; XML-данные при будущем выпуске, не сейчас |
| SpiritualHealthSaveData | spiritualHealthSchemaVersion, sparse organStates, nextEpisodeId, необходимые pending receipts/исторические факты; внутри одного health owner |
| SpiritualOrganState | organId, необязательный acute episode, scar aggregate, destroyed, только необходимые everFormed/activation exceptions; не копия effective HP |
| SpiritualInjuryState | Один acute aggregate с W, peak, episodeId, scar token/decision state; отдельная scar aggregate S со своим treatment ID. Никаких Hediff на каждую царапину |
| SpiritualHealthRules | Чистые функции injury/healing/scar/destruction, integrity/function и action requirements; не вызывает Scribe/RNG/Find |
| SpiritualHealthService | Единственный путь изменения organStates и healing checkpoints, адаптер событий/сохранения |
| SpiritualFunctionSnapshot | Вычисляемые I/activation/function/причины блокировки; только для чтения, не persistent owner |

Realm, Progress, qi, техники/mastery, FinalFoundation/история основания остаются только в HediffComp_Cultivator. Strain остаётся в существующем HediffComp_SpiritualStrain; Ambient — на карте. Данные духовных ран не копируются ни туда, ни в дополнительные health Hediffs/Dictionary. Наш physical-effects слой получает только производные агрегаты: он не хранит W/S/Destroyed и не становится дополнительным источником травмы.

Сохраняемые записи создаются лишь для отличий от профиля. Полностью вылеченный обычный человек может снова не иметь health owner, **если** больше не требуется pending receipt/everFormed факт. Нельзя удалять owner с неразрешённой операцией или необходимой историей ради формального sparse. Здоровый просмотр профиля создаёт только временную view model, не игровые component/Hediff. Все такие классы — проектные предложения, исходники не создавались.

### 16.3. Присутствие, активация и граф функций

Profile resolver сочетает текущий поддержанный species, достигнутые этапы развития из CultivatorState и sparse исключения health owner. У обычного человека Meridians/Dantian/Foundation scaffold/Sea присутствуют dormant с рождения. Golden Core и Nascent Spirit формируются лишь после их Realm. Realm и статус Dormant/Awakened/Advanced не сериализуются второй копией в здоровье.

При обычном повышении Realm отсутствующие поздние структуры появляются целыми **только если они действительно ещё не существовали**. Существовавший destroyed organ остаётся destroyed. Когда будущий добровольный Reforging временно выключает старший орган, необходимые everFormed факты/старые повреждения сохраняет health owner; он не хранит вторую шкалу Realm. Возврат активации не является лечением. Никакого списка missing physical parts или автоматического переноса повреждений в BodyPartRecord.

Dependency graph валидируется как DAG. Собственная Integrity не зависит от повреждения родителя; конкретная функция использует minimum нужных активных integrity. Dormant с I=1 не равен active function=1. Не сформированный орган — distinct state, а не destroyed with I=0. Виртуальная иерархия UI может группировать органы под Spiritual Body, но граф функций не обязан совпадать с деревом отображения.

Неизвестный/удалённый organ/profile ID сохраняется dormant с диагностикой; нельзя превращать неизвестное в destroyed или тихо вылечивать. При отсутствии поддержки расы не применять человекоподобную физиологию автоматически. Race/profile aliases и удаление контента требуют явной migration. Неподдержанная функция блокирует только связанные действия; текущий Realm/знания не удаляются. Требования ещё не реализованных органов в SA-A не регистрируются: старшие техники не отключаются только потому, что Foundation/Core health bridge запланирован на SA-C.

### 16.4. Арифметика и операции повреждения

W/S/базовые 10000 — целые единицы, I и function вычисляются из них. S ограничена 0…9000, W — остатком 0…10000−S; это не два независимо редактируемых HP. Не хранить отдельно maxHp/currentHp/float severity с независимым редактированием. Входной урон квантуется один раз, проверяются finite/nonnegative inputs и bounds; округлённая UI цифра никогда не становится входом следующего расчёта.

Multiple hits обновляют один acute episode органа: W+=acceptedDamage до остатка, peak=max(peak,W). Max/threshold учитывают scars. Первое событие создаёт episodeId и token; дальнейшие попадания не перебрасывают token. Scar calculation при закрытии эпизода использует сохраняемые peak/лечение и один saved result; изменение W→0/S в одной команде. Источник без allowDestruction не выставляет destroyed. SA-A не включает allowDestruction и имеет собственные limits для безопасного теста.

Destruction = явная команда события с разрешённым target organ и выпущенной reconstruction policy. Уничтожение очищает active W, сохраняет S и факт существования, функции читают 0. Reconstruction выставляет destroyed=false, W=0 и canonical reconstruction scar S=5000 как результат **одной** оплаченной процедуры; старый агрегат S не складывается с этой заменой. Последующая терапия лечит этот дефект. Смерть физического Pawn не вызывается установкой destroyed у виртуального органа.

Healing возвращает остаток W/S, события закрытия и производные изменения. Для natural rate хранится маленький целочисленный remainder числителя healUnits×elapsedTicks, чтобы деление на ticksPerDay/скоростной коэффициент не теряло дробные единицы при каждом коротком update. Remainder относится к active healing state, не второй HP; сохраняется, обнуляется корректно при завершении. Шрамы не убывают natural ticker. Recovery modifier один лучший, не сумма всех лекарей.

### 16.5. Сервисы, ограничения Qi и повторное применение

Весь workflow выполняется на игровом потоке: валидировать source/target/event → SpiritualHealthRules → SpiritualHealthService коммитит organ state → CultivationService применяет **только** functional cap qi и доступность действий, при наличии cultivator owner → reconcile наших physical effects/view caches. Реальные функции qiMax и technique eligibility используют актуальный SpiritualFunctionSnapshot. Для обычного человека шаг культивации отсутствует. HealthService не пишет Realm/Progress/quality и не создаёт CultivatorState.

Уменьшение effectiveQiMax=realmQiMax×DantianFunction может отбросить excess personal qi; clamp выполняется после изменения здоровья и на безопасном post-load reconcile, без скрытого energy escrow. Увеличение cap после лечения не восстанавливает отброшенную энергию. Meridians влияют на rate/command requirements, не дублируют cap multiplier. Progress/техники/mastery/Foundation snapshot при этом неизменны. Source/health/strain modifiers имеют отдельные именованные contributions; агрегатор не накладывает один injury penalty через два Hediff.

Идемпотентность исходит от источника операции: attempt/испытание/будущее применение техники хранит stable operationId, outcome payload (organId/amount/scar policy) и applied/phase; load не генерирует новый payload. Пока операция может повториться после load/cancel, target health owner хранит её receipt/результат с необходимым сроком жизни. Повторная доставка того же ID возвращает прежний результат. Не заменять это бесконтрольным lastId или коротким кольцом, которое забывает ещё воспроизводимое событие.

После durable завершения источника и подтверждения невозможности повторной доставки receipt можно освободить; для этого нужен проверенный lifecycle, а не обещание вечной истории всех атак. Default наши источники синхронны и не yield между изменением здоровья/ресурсов/phase. Это не распределённая БД: rollback произвольного exception в середине не обещается. SA0 должен подтвердить порядок save и сценарий pending/committed; при неопределённом состоянии не наносить урон второй раз, сохранить pending diagnostic. До проверки persistent source/target receipts боевые/случайные опасные источники не выпускать.

Ранний deterministic breakthrough не меняется. Поздние failed attempts могут передать один injury payload только после отдельного подключения; costApplied/Progress penalty и injuryApplied различаются, чтобы неточность повторного callback не снимала Progress второй раз. Сам Injury payload никогда не включает изменение Realm/Progress/Q. Voluntary Reforging имеет свой тип команды с явной ценой; он не вызывается из Damage/Heal.

### 16.6. Hediff и physical effects

Роль POC_SpiritualHealth — контейнер persistent health state; у него нет привязки к физическому органу, не предполагается ванильное injury bleeding/tending/death behaviour. Конкретный Hediff base class, lifetime/ShouldRemove, merge, resurrection и отображение проверить на локальных assemblies. Отдельные Wound/Scar/Destroyed существуют внутри virtual state; vanilla severity/stage может быть только вычисленным агрегатом для эффектов, не хранить копию severity каждого органа.

Первый срез не изменяет физические capacities Consciousness и lethal thresholds. Допустим один явно описанный слабый derived effect при серьёзном дискомфорте, если stat hook подтверждён; если нет, оставить функциональные Qi/action ограничения и свой UI. В поздних effects консолидировать штрафы движения/работы до одного ограниченного значения; проверять вместе со Strain и иными модами. Не чистить все Hediffs и не снимать чужую медицину при reconciliation.

Обычный physical damage не вызывает SpiritualHealthService. Отдельный spiritual attack подаёт собственный payload после своих delivery/defence rules; optional dual-body technique описывает два отдельных воздействия и цены. Никакого глобального Harmony postfix на каждый урон ради «связи тел». Verse/DLC/Harmony остаются вне Core.

### 16.7. Сохранения, lifecycle и sparse обновления

spiritualHealthSchemaVersion независима от cultivation schema. Сохраняются organId, W/S, destroyed/необходимые everFormed факты, peak/token/scar outcome phase, healing remainder, treatment checkpoints и pending receipts. Кеш функции, дерево UI, профили Def и runtime список раненых производные. После load: версия/migration → ссылки/aliases → validation → восстановление функций → однократный qi clamp/effects reconcile. Нельзя в FinalizeInit автоматически «создавать» здоровый Golden Core поверх destroyed.

**Старый здоровый save без health записи = здоровая профильная анатомия.** Старые культиваторы получают уже положенные Realm органы здоровыми, если записи об их травмах никогда не было; новые случайные раны не генерируются. Миграция сохраняет CultivatorState и FinalFoundation; этот health module не выполняет повторную Foundation assessment. Невалидные отрицательные величины нормализуются с диагностикой, неизвестные IDs сохраняются без превращения в потерю органа; конфликтующие дубли владельца требуют явной repair policy, не молчаливого суммирования ран.

State следует Pawn при caravan/despawn/смене faction/карты, без ссылки на текущую Map как owner. Первое правило для вне карты/контейнера/криптосна/мёртвого: естественное духовное заживление и терапия приостановлены, данные сохраняются, после возвращения нет catch-up. Если позднее потребуется caravan healing, это отдельный проверенный режим. Воскрешение возвращает существующие травмы, не лечит духовное здоровье по умолчанию и не выдаёт новый event token; стандартное игровое resurrection behaviour проверить отдельно. Discard Pawn не предотвращается ради здоровья, runtime индексы освобождаются; копирование/клонирование сторонними модами не считается автоматически поддержанным.

Здоровые dormant Pawn не тикают из-за этой системы. Редкие проверки нужны только владельцам с active W/лечением/pending reconciliation (проектно раз в 250–1000 игровых ticks с разнесением); scars/destruction без активного лечения не требуют постоянной симуляции. Предпочесть проверенный interval callback единственного health Hediff. При fallback manager он хранит только временный индекс активных owner, не damage state и не WorldPawn retention. Полный обход всех Pawn каждого tick запрещён; один rebuild индекса при load допустим по реальному сохранённому списку карты.

Realm/травма/лечение/profile change инвалидируют snapshot только соответствующей пешки. Обычные movement/graphics callbacks не пересчитывают историю и не начисляют лечение. Нельзя использовать чтение UI/stat как таймер лечения; delta учитывается ровно один раз независимо от частоты открытия окна. Natural Recovery и paid treatment не добавляют обычный Progress.

### 16.8. Health UI: цель и временный интерфейс

Точный health tab/ITab extension point **не подтверждён** для установленной RimWorld 1.7. Read-only spike: найти настоящий Health UI path, публичные callbacks/draw layout, selection lifecycle, виртуализацию списка и возможности добавить switch без BodyDef changes. Проверить необходимость узкого Harmony patch и взаимодействие с полной заменой Health сторонними модами. Не придумывать target method по коду 1.6.

View model общего SpiritualAnatomyPresenter получает profile + sparse snapshot и строит дерево: Spiritual Body → органы → acute/scar/destruction/лечебные действия. Physical Anatomy renderer остаётся игрой. Цель — switch Physical/Spiritual в контексте здоровья; если стабильной точки нет, собственный Window_SpiritualAnatomy с похожим деревом, выбранной пешкой и возвратом к обычному Health. Вход из выбранного Pawn/собственного меню мода проверяется отдельно, он не требует статуса культиватора или CultivationSpot. Переключатель в vanilla Health остаётся отдельным UI milestone, а не молча объявленной выполненной функцией.

UI показывает presence/activation/I/MaxIntegrity раздельно, причину dependent block, способы лечения и стоимость, не смешивает Foundation organ со значением Q. При недоступном ещё Realm будущий орган серый/свёрнутый «не сформирован», destroyed — явный красный статус. Только нужные строки/локализованный кеш на selected Pawn, без сканирования всех органов всех NPC на кадр. Preview не сохраняет новый state. При отмене Harmony target не должен ломаться health backend; временное окно остаётся рабочим.

### 16.9. SA0 и приёмка по этапам

SA0 = Q54–Q60 и Q64 из RESEARCH, перед SA-A; Q61–Q63/Q65 нужны последующим расширениям. Ни один вопрос не включать в MVP/T0/FQ0/AQ0 автоматически. До игрового включения источник/лечение и собственное окно проверяются без DLC; отсутствие нужных UI hooks не оправдывает патч physical body.

Core fixtures: presence/dormant/active/destroyed/not-formed; W/S saturation и order-independent суммы; повреждение/заживление не меняют Realm/Progress/mastery/Q/P; peak/token/scar once; destruction только с разрешением; восстановление базового органа до 50%; dependency блокирует функцию, не травмирует соседний орган. Числовой пример S=2000,W=3000 → I=0.5; после W=0 I=0.8; после S=0 I=1. Effective qiMax=20 при DantianFunction=0.5 даёт 10, qi=18→10; лечение возвращает cap=20, qi остаётся 10, не 18.

Save/game matrix: обычный взрослый без CultivatorState и культиватор; dormant injury до пробуждения; старый здоровый save; частичный W/Scar/Destroyed, scar decision до/после закрытия эпизода, same event дважды, 10 reload, cancel/платный checkpoint, переход карты/караван/фракция, смерть/возрождение, новая ступень при уже существующей травме, missing profile/organ Def, Base без DLC. UI просмотр здорового Pawn не создаёт owner. Реальные прошедшие проверки фиксируются по build; в текущем предпроекте все game/API пункты pending.

Перед SA-B: базовая реконструкция последнего культиватора с нулевой собственной Qi и обычного человека, repair обеих разрушенных базовых структур без deadlock, cap не отрицательный. Перед старшими organs: GoldenCore с destroyed core сохраняет Realm и техники; Exceptional/GoldenCore с Foundation I=0 сохраняет Q, после ремонта доступ возвращается без повторной Formation. Перед боевым модулем: защита обычной колонии, LOS/delivery/cooldown, бюджет угрозы, отсутствие духовного урона от обычных bullets.

Performance: одна и та же сцена 100/500 здоровых поддержанных NPC, отдельно 0/10/50 injured, две карты и 0/10 selected UI повторных открытий; спящие scars/destruction без healing; серия spawn/despawn. Измерить baseline с текущими Ambient/Beast системами и без SpiritualHealth, TPS, median/p95 update, allocations/UI, save size/load и retained Pawn. Цель — ≤3% дополнительной медианной потери TPS на поддерживаемом диапазоне, без таймеров у здоровых/утечек индекса; это проектный gate, не измеренный результат. Существующие perf gates других модулей сохраняются, совокупный бюджет оценить перед совместным release. Если не помещается — реже active updates, меньше визуальных пересчётов/источников, не ослабление save-инвариантов.
