# Path of Cultivation — правила работы с Codex CLI

Дата: 14 октября 2026 года. Среда: Windows/Steam, Docker Desktop, Git; работа с OpenAI API, без MCP.
Минимальный мод уже существует: Source/PathOfCultivation.csproj (net10.0), минимальный Mod-класс и About/About.xml. По согласованному заданию он собран в Docker с .NET SDK 10 и загружен в RimWorld 1.7 unstable/WaylithCLR. Это не подтверждает Feature API; manifest B00 и воспроизводимость B01 остаются pending. Доступ агента к игре, DLL и Docker определяется конкретной сессией.

## 1. До первого API-запроса

API-баланс сейчас $0 по исходным условиям. Подготовка репозитория, refs и checklist возможна без API; для выбранного режима нужны оплаченная возможность API и доступная модель. ChatGPT Plus не является пополнением API. Не запускать платные retry в надежде, что подписка оплатит запрос.

Текущая официальная документация различает ChatGPT authentication и API-key authentication: последний оплачивается по API-тарифам. Выбранный процесс использует именно его. Источник: [Authentication](https://learn.chatgpt.com/docs/auth).

Перед работой проверить codex --version, codex --help и доступные опции установленной версии. Закрепить CLI version; не копировать старые флаги из инструкций 2025 года. Сверить модель с доступом своего API-проекта и текущим тарифом, не переносить сокращения из веб-интерфейса в model ID.

Для API login официальная инструкция показывает передачу ключа через stdin в codex login --with-api-key. Секрет должен поступать из приватного окружения или secret provider, а не из literal команды, истории shell, Dockerfile или файла репозитория.

## 2. Права и окружение

Рабочий каталог агента — отдельный repo. Игровые DLL доступны только через выделенный read-only mount. Игру запускает разработчик Windows; agent container не управляет Steam или обновлениями.

Применить настройки из TECHNICAL_DESIGN: non-root, без capabilities и новых привилегий, без docker.sock, root read-only, ограниченные CPU/RAM/pids и writable repo/cache/tmp. Не монтировать диск C целиком, домашнюю папку, credential store, личные git/SSH credentials.

Два сетевых режима:
- Offline build: сеть отключена, restore предварительно завершён.
- API agent: сеть через проверенный proxy/firewall с разрешением необходимых OpenAI endpoints, без произвольного интернет-доступа. NuGet/CLI download — отдельный bootstrap без API-ключа.

Docker bridge не создаёт allowlist сам по себе. TLS-проверку не отключать. Проверить положительный доступ к разрешённому API и отказ к контрольному запрещённому адресу до автономной работы. Конкретные endpoint устанавливаются по фактическому client config; не выдумывать полный список заранее.

Ключ нужен процессу CLI; полностью скрыть его от другого кода с тем же доступом к процессу нельзя. Для более строгой границы использовать отдельный доверенный API gateway, удерживающий upstream key вне agent-контейнера; это дополнительная инфраструктура, не обязательный MVP. Не обещать, что environment variable сама по себе защищает секрет от агента.

Без MCP работа выполняется чтением подключённых файлов, shell-командами, git и локальными build tools. Внешние приложения/аккаунты не нужны.

## 3. Секреты и данные

Запретить чтение/печать secrets, env dump, auth.json, credential caches и shell history. Правило — дополнительная защита, не замена ограничения прав.

Key имеет минимально достаточные разрешения отдельного API project. Не включать auto-recharge на первом пилоте. auth.json и другие auth caches хранятся вне repo с ограниченными правами; официальный документ предлагает keyring и другие credential store режимы. В контейнере без keyring проверить supported ephemeral-вариант либо приватный writable каталог, который уничтожается после сессии.

Не передавать полный game DLL, декомпиляцию всей игры или личный save в prompts. Для API-задачи дать нужные публичные сигнатуры, свой адаптер и минимальный очищенный log. Код/вывод, прочитанный агентом и использованный в контексте, может уходить в API; локальное выполнение не означает, что модель никогда не получает содержимое файлов.

Перед commit/package проверять staged diff, allowlist выходных файлов и секреты. .gitignore не удаляет ранее закоммиченный ключ. При утечке сначала revoke/rotate, затем очистить историю и artifacts; не ограничиваться удалением строки.

## 4. Экономия токенов и денег

Бюджет — решение разработчика, не гарантированная стоимость. Начать с пилота: до $5 за несколько узких задач; затем установить личный месячный предел, например $20–30, и пересчитать по реальному usage. Не пополнять автоматически, не покупать большой баланс до T0.

Для каждой сессии записывать task ID, model ID, input/cached input/output usage и стоимость по dashboard. Учесть reasoning и tool/context overhead по фактическому billing. Уведомления project budget не считать гарантированным hard cutoff: локальный процесс должен останавливаться по выбранному денежному/временному пределу, с запасом на запаздывание статистики.

Формула без cache writes: C=(I_uncached×P_input + I_cached×P_cached + O_billed×P_output)/1,000,000. Если применимы cache writes, long-context надбавки, fast-tier или другие услуги — добавить их отдельно. Считать все итерации задачи, а не только финальный ответ.

Пример чувствительности, не тариф: при 20,000 uncached input и 5,000 billed output задача стоит $0.09 при ставках $2/$10 за миллион; $0.45 при $10/$50. Двадцать аналогичных задач — $1.80/$9, но реальные контексты и retries меняют сумму. Актуальные цены проверяются на [Pricing](https://developers.openai.com/api/docs/pricing).

Рабочие правила:
1. Одна задача: обычно 1–3 файла, один проверяемый результат.
2. Давать ссылки на нужные разделы docs и точные символы, не все семь документов в каждом prompt.
3. Сначала искать rg/rg --files, затем читать ограниченные фрагменты; не загружать весь repo.
4. Заканчивать тесты после релевантного успеха; не делать десять одинаковых запусков.
5. После двух неудачных вариантов исправления одной ошибки остановиться, показать гипотезы и требуемую проверку.
6. Обычный режим рассуждения — низкий; средний включать для persistence/API diagnosis и неоднозначных ошибок. Более глубокий режим — только на конкретную проблему.
7. Выбирать самую дешёвую доступную модель, которая проходит короткий одинаковый пилот по качеству; сложную задачу эскалировать после установления причины. Доступность и способности конкретной модели не считать доказанными по цене.
8. Сохранять короткий progress note: что изменено, точный build, следующий task, нерешённые вопросы. Новая сессия читает note и relevant docs вместо пересказа всей истории.
9. Не запускать несколько агентов параллельно без отдельной причины и установленного бюджета.

Prompt caching может уменьшать цену повторяющейся части контекста, но его эффективность проверяется usage; не обещать фиксированную скидку. Batch — возможный инструмент для независимых offline запросов, но не замена интерактивному циклу CLI по умолчанию.

## 5. Правила кода и scope

- Реализовывать только принятое B00–B09. Новая идея оформляется в backlog, не включается в текущий diff.
- Минимальный bootstrap уже реализован; новые игровые исходники создавать только в рамках согласованной задачи MVP. Не повторять подготовительный этап по устаревшему checklist.
- Сначала проверить выбранный game build и references. При неизвестном API исследовать сигнатуры, не угадывать chain вызовов.
- Core не зависит от Verse/RimWorld. Единственный owner — HediffComp; UI не мутирует state напрямую.
- Не менять DefName, packageId, save-поля и schemaVersion без migration.
- Не заменять JobDriver анимацией и не считать progress реальным игровым временем.
- Не добавлять Harmony/VEF/DLC как shortcut без ADR о необходимости.
- Не писать generic framework для одного IronBody.
- Не исправлять unrelated style и не перестраивать весь repo в рамках одного Job.
- Не копировать код конкурента без проверки лицензии и отдельного решения. Идеи сравнивать, implementation писать самостоятельно.
- DLL игры приватны и read-only; не коммитить, не публиковать, не править.
- Коммиты и tags только по поручению; не делать push/Workshop publish из задачи «реализуй функцию».

## 7. Проверки в рабочем цикле и перед коммитом

Цикл: Analyze → Review → Implement → Review → Verification → Commit. Review согласует план и затем проверяет diff на соответствие заданию; Commit выполняется только по явному поручению.

- Analyze определяет проверки наблюдаемого поведения, существенных границ и ошибочных входных данных для новых и изменяемых расчётных правил MVP, а также доступный способ их выполнения. Неопределённая семантика входов требует согласования, а не закрепления догадки тестом.
- Implement добавляет или обновляет относящиеся к задаче автоматизированные тесты в пределах согласованного scope. Для исправления воспроизводимой логической ошибки по возможности добавляется регрессионный тест. Тесты проверяют требования, а не повторяют реализацию.
- Отдельный тест для каждого поля, простого объявления Def или косметической правки не требуется. Обязательного процента покрытия, 100% coverage и квоты числа тестов нет.
- Если нужной инфраструктуры нет, её подготовка требует отдельного согласованного шага перед запуском соответствующих тестов. Не добавлять framework, зависимости, CI или инструмент coverage без отдельного согласованного задания; не создавать ради этого новую обязательную backlog-задачу автоматически.
- Verification учитывает сборку, автоматизированные тесты и игровые проверки раздельно. Успешная сборка или unit tests не доказывают загрузку Defs, сохранение/загрузку состояния и работу мода в RimWorld. Игровые сценарии выбираются по затронутому поведению, без полного ручного прогона после каждой правки. Непроведённые проверки остаются pending и не записываются как успешные.

1. Сопоставить diff с task acceptance; показать новые зависимости.
2. Выполнить необходимые для изменения build и релевантные автоматизированные проверки доступными средствами; отсутствие средств и невыполненные проверки указать явно.
3. Проверить затронутые игровые сценарии, в частности при изменении Jobs, Scribe, Def или UI.
4. Просмотреть git diff --check, staged paths и secrets; не делать blind git add всего каталога.
5. Обновить compatibility report/ADR только при фактическом изменении.
6. Commit после проверки; незакрытая in-game проверка остаётся явно pending и блокирует release.

Формат отчёта Implement: изменено → почему → выполненные команды и результаты отдельно для сборки, автоматизированных тестов и RimWorld → непроверенные сценарии и причины → риск/следующий шаг. «Собрано» и «проверено в игре» — разные утверждения.

Рекомендуемый короткий AGENTS.md при начале реализации: scope B00–B09; pinned build; docs authoritative; Core rules; no secrets/game DLL; no DLC/Harmony without decision; no unverified API; обязательная фиксация pending checks. AGENTS.md и минимальные исходники уже существуют; действующие инструкции AGENTS.md обязательны, менять их без поручения не следует.

## 8. Spirit Beasts: ограничения будущей разработки

До отдельной задачи на 0.4.1 реализация животных запрещена scope: не добавлять animal C#/XML, UI, тик, виды, эволюцию, ядра, договоры или DLC. Документация §13 GDD/TECHNICAL_DESIGN описывает будущий дизайн, а не поручение его реализовать. B00–B09 и срок 10 ноября не расширяются.

- Сохранять общий CultivatorState и единственный HediffComp_Cultivator. Core оперирует числами/ID/snapshot; признаки Humanlike, faction, возраст и доступные действия проверяет адаптер. В 0.1.0 человеческий допуск остаётся строгим.
- Не строить наследование Human/Beast, species framework или отдельный progress storage до работающего среза. В 0.4.1 достаточно профиля видов, функции допуска и отдельного updater/presenter.
- Различать допустимость носителя и доступность действия. Приручение/одичание не удаляют state. Животным не выдавать человеческие JobDriver, Window actions, свитки, training или Ability по факту общего Pawn.
- API сверять с точным build 1.7. Не переносить CompPostTick/Interval, maturity, WorldPawns, training и animal combat из decompile/гайда 1.6. Не заявлять SB0 закрытым по одному опубликованному анонсу; фиксировать найденные signatures и ручные результаты.
- Не добавлять state всем животным. Обновлять лишь пробуждённых, редко и с разнесением нагрузки; никаких глобальных Pawn scans/allocations каждый tick. Не сканировать источники среды каждому зверю заново. Сначала профиль, затем выбор callback или минимального индекса; не реализовывать оба механизма сразу.
- Не начислять практику за пропущенное off-map время, паузу или время до загрузки. Сохранять дневной бюджет, отменять незавершённое ожидание без награды. Runtime индекс не должен удерживать discarded Pawn.
- Поддержку модового животного объявлять только по opt-in профилю и проверке нужд/тела/здоровья/зрелости/дрессировки/эффектов. Отсутствующий профиль — dormant, не тихая замена видом человека. Не обещать сохранность save при удалённом race mod.
- Новые save-поля добавлять миграцией при выпуске системы, не заранее. Для договоров проверить разрыв ссылок, для ядер — одноразовую выдачу и resurrection до добавления контента.
- Матрица 0.4.1: без DLC; поддержанные vanilla виды; один отдельно проверяемый модовый вид перед заявлением совместимости; приручение/одичание; caravan/off-map; смерть/возрождение; отсутствие rest need; старый человеческий baseline. Зафиксировать нагрузку для 100/500 животных и 0/10/50 пробуждённых по TECHNICAL_DESIGN §13.5.

Последовательность заданий после 0.4.0 — ROADMAP §4.1. Одно задание закрывает один результат: read-only исследование → общий state на одном звере → пассивный рост → переход/пассив → UI → regression. До этого никакие SB0/animal эксперименты не отнимают резерв MVP.

## 9. Ambient Qi: ограничения будущего этапа

Документация GDD/TECHNICAL_DESIGN §14 не разрешает реализацию среды в B00–B09. В предпроектной задаче менять только документы; C#/XML не создавать. Первый рекомендуемый срез — 0.4.2 после 0.4.1 и AQ0; задачи брать последовательно по ROADMAP §4.2.

- Qi в текущем state — Personal Qi. Не хранить ambient density/reservoir у культиватора и не выдавать обычным людям/животным CultivatorState ради расчёта воздействия. MapComponent_AmbientQi владеет полем, отдельный Strain Hediff — персональной перегрузкой.
- Окружение подаёт snapshot и множители в существующий сервис; actual-toil и beast updater остаются единственными источниками разрешённого Progress/Qi. Наставник и среда используют согласованный суммарный cap, первая гарантированная попытка не становится случайной.
- Первый scope — аналитические круги, max источников/min ограничителей, не сумма. Не добавлять клеточную grid, diffusion, загрязнение, гены, физику комнат, граф формаций или растения «для полноты».
- PollutionGrid/Biotech нельзя использовать как готовый слой базы. Изучать доступность только read-only и явно отмечать build/DLC; primary пример мода 1.6 не подтверждает API 1.7. База не импортирует DLC types/Defs и не зависит от VPE/VEF.
- Не сканировать карту/мир/все Pawn каждый tick. Редкие окна, локальные buckets и cache с map+position+revision; finite worst-case и допустимый максимум источников проверяются профилем. Rendering не выполняет симуляцию и не пересоздаёт full-map texture каждый кадр.
- Источник на карте имеет одного владельца. ThingComp здания не хранит копию заряда/интенсивности. Rebuild индекса производный, идемпотентный; spawn/despawn/power/save не создают невидимых дубликатов.
- Старый save без ambient секции получает D=0, не новую жилу. Генерация только один раз на новой карте; при неподтверждённом hook перейти к добровольному событию. Load не начисляет exposure/practice за прошедшее время и не меняет выбранный исход попытки.
- Перегрузка обратима и объяснима; видимые границы и способ контроля обязательны. Отдельно проверить обычных людей, гостей, животных без CultivatorState, культиваторов и неподдержанные расы. Стены не экранируют по умолчанию; растения первого среза не меняются.
- Индивидуальные A/V без новых данных равны 1; не подменять Affinity устойчивостью или вероятностью пробуждения. Генетическую интеграцию не добавлять в базу. Не раздавать скрытые random stats всем существам при load.
- Проверки: max/min и границы; 10 load, old save, power toggle/move/remove, несколько карт, off-map/контейнер, сохранившийся S, наставничество/beast cap, DLC-off. Нагрузочная матрица и целевые gates — TECHNICAL_DESIGN §14.8. Без локальной игры помечать соответствующие пункты pending.

При неизвестных hooks сначала записать вопрос Q32–Q44 и точный эксперимент. Если простой круг требует масштабной переработки owner/AI, выбрать минимальную альтернативу из технического проекта или отложить выпуск. Не расходовать резерв MVP на эти эксперименты.

## 10. Foundation Quality & Age: правила будущего среза

В этой задаче менять документацию, не писать C#/XML/ресурсы. В 0.1.0 не добавлять возрастную кривую, foundation поля, часы подготовки, качество, новые проверки RNG или child code. MVP_BACKLOG и допуск 18+, I→II без RNG, rates/caps и срок 10 ноября остаются прежними. Взрослый срез уточняет будущую 0.4.0; дополнительные вехи ROADMAP §4.3 пока предложения.

- Foundation Quality не равно POC_Foundation, Progress, Qi Affinity или Instability. До Formation хранить ограниченную подготовку и вычислять прогноз; окончательный snapshot только после успеха. Единственный owner прежний HediffComp_Cultivator, все изменения через CultivationService.
- Значимое раннее начало — реальные age-weighted часы первых H, не дата вступления/ранний клик и не возраст в момент прорыва. Никаких ретроспективно выдуманных детских занятий, aging tick-штрафов и снижения качества старого мастера.
- Проверять target ceiling и наличие контента до probability clamp/RNG/расходов. Weak не проходит QiGathering→Foundation; Ordinary проходит при остальных условиях. Exceptional не открывает Transcendence, Flawless не выдаёт Immortal.
- Повторная подготовка — целое новое bounded окно при сохранённом доказанном P. Не суммировать бесконечные часы/лучшие отдельные факторы разных окон и не делать RNG качества. Mentor/ambient speed не умножают часы.
- Использовать один источник Affinity; до Ambient Qi E=0, без MapComponent/DLC. Наставник помогает реальным временем/знанием, высокий Realm не заменяет компетентность. Не расширять animal I→II человеческой программой.
- Save сохраняет агрегаты, preparationRevision, snapshot и token прежней попытки. Ни load, ни отмена того же незавершённого snapshot не выдают новый token. Не сбрасывать качество/улучшения сменой пути, смертью или омоложением.
- Legacy пешкам не выдавать Weak/Flawless по предположению. Сохранять Realm/knowledge/mastery и защищённый достигнутый ранг; подготовку/assessment выполнять без отката, future gate объяснять в UI.
- Thresholds/ceilings/profiles валидировать, symbolic будущий rank отличать от отсутствующего реализованного Def. Неизвестные category/policy IDs не стирать; неверная конфигурация диагностируется и блокирует связанную операцию.
- Проверить числовые границы, early-click, неодинаковые биологические возраста, delta partition, несколько одинаковых окон, RNG snapshot до/после финальной фазы, 10 load, старые развитые saves, base-only и отсутствие animal regressions. Не объявлять API 1.7 подтверждённым по старому гайду.

Возрастные/child/learning/age-reversal hooks исследуются по Q45–Q53. Никакой автоматической выдачи learning need или переноса человеческих возрастов животным. Полную перестройку/сокровища/новые DLC не объединять с 0.4.0; предложение минимального укрепления оформлять отдельной задачей после базовой приёмки.

## 11. Spiritual Anatomy: инварианты будущего модуля

Текущая задача — только документы. Не создавать классы, XML/Defs, textures, UI или resources. Spiritual Health не включается автоматически в 0.1.0–0.4.2 или другой текущий milestone; SA-вехи ROADMAP §4.4 — предложения без принятого номера. MVP_BACKLOG не меняется, срок около 10 ноября сохранён.

- Virtual anatomy предпочтительна. Не менять BodyDef/BodyPartDef и global physical damage ради «второго тела». Health switch исследовать по реальным 1.7 symbols; при нестабильном patch использовать своё окно, честно оставляя native switch pending.
- Spiritual Body есть у поддержанного обычного человека с рождения; здоровый профиль вычисляемый, state lazy. Не выдавать CultivatorState обычному Pawn для органов/травмы/доступа к просмотру.
- Единственный owner ран/шрамов/Destroyed — POC_SpiritualHealth/HediffComp_SpiritualHealth. Cultivator owner сохраняет Realm/Progress/Qi/Foundation/техники; Strain и Ambient сохраняют прежних владельцев. Не дублировать damage в отдельных Hediff/Dictionary/state.
- Damage/Heal никогда не меняют Realm, Progress, techniques/mastery, FinalFoundation или возрастной imprint. Объявленная failed-attempt cost и добровольный Reforging — отдельные операции, не Injury side effect. После repair не требовать новых прорывов уже достигнутых рангов.
- Presence, activation, I, dependent function и Destroyed различать. Not formed не равно missing/destroyed; пробуждение/новый Realm не лечат существующую травму. Функциональное блокирование зависимого органа не наносит ему damage.
- Хранить integer W/S и один destroyed, вычислять I/caps; не обновлять старые float coefficients умножением. Meridians rate и Dantian storage применять один раз. qi clamp допускает потерю энергии, не отрицательные числа/скрытый резерв/возврат избытка при лечении.
- Source operationId/payload и receipt/phase сохраняются; scar token один на acute episode. Повторный callback/load не наносит новый урон, не списывает стоимость и не перебрасывает шрам. Pending receipt не удалять коротким кольцом или вместе с вылеченной раной до durable завершения источника.
- Тикать только active W/лечение, интервально; не сканировать всех Pawn/мир, не healing из draw/stat getter, не удерживать discarded Pawn. Off-map/dead/container healing первого среза заморожено без catch-up.
- Destruction разрешать лишь когда доступна конкретная реконструкция без зависимости от утратившейся функции. Проверить помощь dormant/последнему культиватору, отсутствие Qi пациента, два разрушенных базовых органа, paid checkpoints/cancel/load.
- Ambient 0.4.2 — только обратимая Strain. Любой injury bridge позже отдельно; human organs/age/Jobs животным автоматически не давать. Spirit Beasts baseline неизменен.
- Обычные пули/медицина не становятся spiritual damage/healing. Для будущего боя отдельные delivery/defence/threat budget; не вводить безусловный armor-bypass или death при уничтожении виртуального «сознания».

Обязательная матрица и SA0 — TECHNICAL_DESIGN §16.9 / RESEARCH Q54–Q65. Успешная pure arithmetic не закрывает Health UI/Scribe/lifecycle. В агентском отчёте отделять выполненные checks от game checks pending; не добавлять Harmony зависимость в ранние выпуски ради будущего интерфейса.
