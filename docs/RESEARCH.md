# Path of Cultivation — предпроектное исследование

Дата проверки: 14 октября 2026 года, Europe/Moscow.
Метод: открытые официальные публикации, страницы авторов Workshop, доступные репозитории и документация.
Первоначальное исследование не включало локальную установку, Steam Workshop binaries, DLL и игру; интервью и игровые сравнения не проводились. Дополнение 15 октября 2026 года фиксирует bootstrap по подтверждённым фактам согласованного задания .codex-tasks/task.md и структуре исходников; новые игровые тесты при этой синхронизации не выполнялись.

## 1. Шкала доказательности

- **F — подтверждённый факт:** содержится в открытом первичном источнике; характеризует его дату/версию.
- **A — заявление автора:** функция описана автором, но её работоспособность в игре не проверялась.
- **D — проектное решение:** предложено для Path of Cultivation.
- **H — гипотеза:** требует плейтеста, исследования DLL или актуального комментария разработчика.
- **U — неизвестно:** источник не даёт надёжного ответа.

Отсутствие функции в описании не доказывает отсутствие её в моде. Workshop tag 1.6 не доказывает невозможность работы на 1.7; совместимость оценивается отдельно как declared и tested.

## 2. RimWorld 1.7: что установлено

**F:** официальный анонс Ludeon от 12 октября 2026 сообщает о переходе с Unity на собственный Waylith и доступности 1.7 в Steam unstable. В анонсе основная ветка ещё 1.6. Автор заявляет совместимость большинства старых модов и просит отмечать поддержку 1.7 после тестирования. Дата stable там не указана. [S01]

Следствие D: планировать релиз мода на 10 ноября независимо от stable; использовать game build manifest и повторять smoke после обновления.

**F/A:** исходный проект FasterGameLoading—Continued разделяет сборки 1.6 и 1.7; для 1.7 описывает .NET 10 и ссылки на Assembly-CSharp.dll, UnityStubs.dll, Waylith.dll и установленный Harmony. [S02] Это первичный пример моддера, не общая гарантия API.

**D, реализовано для bootstrap:** .NET SDK10/net10.0, SDK-style и явные игровые references. Применимость этого target подтверждена сборкой минимального мода в Docker и его загрузкой в игру по согласованному заданию; функциональные API требуют отдельных проверок.

**F:** Microsoft документирует .NET10 как LTS; global.json позволяет управлять выбором SDK, а SDK-контейнеры подходят для build. [S03–S05] Это подтверждает tooling, а не игровой runtime пользователя.

**F:** у автора Harmony опубликована 3.0.0-rc.2 как prerelease. [S06] **U:** нужная конкретной установке RimWorld версия и правила совместной загрузки. **D:** MVP не требует Harmony, потому что выбранный цикл строится на собственных предметах, Jobs и Hediffs.

Обнаруженная community-страница [S07] приводит рекомендации net10.0, новые DLL и Harmony3. Она полезна как список проверок, но не используется как единственное доказательство технических требований. Официальный primer не был получен. Точные API подтверждаются установленными assemblies, а не переписыванием учебника1.6.

### 2.1. Локальный bootstrap: verified / pending / assumptions

Подтверждено разработчиком: минимальный мод собран в Docker с .NET SDK 10/net10.0 и успешно загружен в RimWorld 1.7 unstable с WaylithCLR. Независимый протокол проверки, build manifest и остальные критерии B00/B01 пока не оформлены.

**Pending B00:** точный game build, branch identifier, runtime/assembly metadata, фактические пути, версии и SHA-256 DLL, точная версия SDK, путь Player.log и очищенный протокол. Эти значения не предоставлены, поэтому здесь не подставляются. **Pending B01:** закрепление SDK/image/packages, clean offline build, output allowlist, повтор в новом контейнере с теми же refs и Core-only запуск с проверкой metadata/ошибок. Dockerfile использует тег sdk:10.0 без digest, проект использует локальные References/; это не доказательство полной воспроизводимости. B00/B01 полностью не закрыты; оставшиеся критерии должны быть проверены до начала B03.

**Pending Feature API Verification:** Def — B02; HediffComp и Scribe — B03; ThingComp/Window — B04; JobDriver, Toils, reservation, needs и прерывания — B05, сценарии прорыва — B06, чтения — B07; stat/Hediff effect — B07. Сохранение активных Jobs проверяется в B05–B07, общая регрессия — B08. Минимальная загрузка эти API не подтверждает; signatures и результаты тестов пока не зафиксированы.

**Assumptions / H:** предложенные адаптеры и их runtime-поведение остаются гипотезами до проверки задачей-владельцем. Успешный bootstrap не доказывает работу сохранений, UI, механик или совместимость со следующим build. Минимальные условия B02 из MVP_BACKLOG выполнены на уровне подтверждённого bootstrap; в рабочей сессии должны быть доступны references. Открытые проверки API B03–B07 не блокируют начало B02.

### Ascension

A: автор указывает совместную работу с Cultivator of the Rim и tutorial wiki. В author comment различаются body и essence варианты; qi barrier требует энергии. Описание предлагает дополнительный JobsLimitTweak при лаге у максимальных культиваторов и упоминает placeholder-текстуру body techniques. [S08]

UX-гипотеза: сложность может потребовать отдельного обучения; наличие wiki само по себе не означает плохой UI. Плейтест нужен для проверки требований, понятности и поздней производительности. Wiki [S15] при открытии вернула403; её содержание не использовано. Нельзя сравнивать её детали по памяти или поисковому сниппету.

Актуальность: открытая страница показывала последнее обновление5 октября и162 change notes; tag1.7 отсутствовал. Дата страницы не даёт semantic version кода. Release binaries не скачивались.

### Cultivator of the Rim

A: вход через предметы; накопление рядом с источниками Qi и прорывы. Royalty Meditation используется для расписания; It's Sorcery и Vehicle Framework предлагаются как дополнительные integrations, не обязательные зависимости. FAQ описывает сценарное включение NPC-культиваторов и не обещает безопасное добавление mid-save. Автор указывает work-in-progress wiki и dev repository. [S09–S11]

UX-гипотеза: знакомое расписание Royalty уменьшает обучение у владельца DLC, но обязательность DLC повышает порог входа. Из описания нельзя вывести качество всех техник или интеграцию Ideology. Страница показывала обновление31 мая и114 notes. Точные release номера не установлены.

### RimImmortal

A: Core описывает внутриигровой tutorial, духовные корни, развитие и книги. В Known issues указаны трудности прорывов и рекомендации по ritual-related исправлению. В metadata Required DLC перечислены Royalty и Ideology, а текст утверждает необходимость трёх DLC: это не согласованная спецификация, Biotech требует отдельной проверки. [S12]

A: Faction добавляет две секты, систему вклада/титулов, культуры, мемы и sect ships. [S13] Следовательно, «секты и Ideology никогда не реализованы у конкурентов» — неверная позиция.

UX-гипотеза: tutorial помогает входу, но многопакетность и DLC увеличивают матрицу совместимости. Known issues — свидетельство авторской оговорки, а не измеренная частота багов. Core показывал обновление21 июля, Faction21 июня. Не переносить требования Core на самостоятельные части серии.

### 武道 / Martial Arts

A: автор связывает вход с боевым навыком≥10 и руководствами; раздельно описывает Ци и опыт, тренировку/медитацию и техники. [S14] Это релевантный уся-конкурент и показывает, что отдельные progress/qi не являются доказанной уникальностью Path of Cultivation.

UX-гипотеза: режимы work/UI знакомы RimWorld, но реальное удобство, сохранения и balance надо проверить. Страница показывала обновление7 октября. Комплект DLC по коду и работа1.7 неизвестны.

### Ограничения Workshop retrieval

В извлечённых Steam-страницах встречались общие banners «removed/incompatible», несмотря на доступные описание и metadata. Не считать их доказательством удаления или несовместимости конкретно с1.7 без независимого подтверждения. Использованы явные tags, Required items и авторское описание.

Даты без года переданы так, как отображены на просмотренной странице. Кеш поиска иногда показывал более старую дату, чем открытая страница; при сравнении использовалась последняя. Ни один tag не заменяет локальный launch test.

## 4. Ниши и позиционирование

Подтверждённый вывод: жанр уже представлен, и даже секты/мемы имеются в серии RimImmortal. Отдельные Ци/опыт и техники также представлены. Поэтому идея не уникальна сама по себе.

Гипотезы возможностей:
1. Небольшое начало без обязательного DLC.
2. Понятные требования/цены и ограниченное число новых предметов.
3. Школа с отношениями и управляемой передачей знаний как центральная петля.
4. Умеренные ранние усиления и сохранение хозяйственной цены занятий.
5. Прозрачная поддержка save/schema и конкретных game builds.

Нельзя утверждать, что у конкурентов нет наставничества, политики знаний или таких UX-решений: доступные источники не дали исчерпывающего ответа. Наше отличие должно подтверждаться собственным продуктом и сравнительным плейтестом.

До выпуска0.2 провести одинаковый сценарий в доступных конкурентах: чистый mod list, вход,10 дней практики, первая техника, save/reload, требования DLC, время изучения UI. Не смешивать конкурентов в одном save при измерении баланса. Выводы вне этого исследования.

## 6. Инфраструктура и API: подтверждённое и решения

F: официальная OpenAI authentication документация различает subscription sign-in и API-key usage, показывает stdin login и описывает caches/credential store. [S16] D: используем API key выбранного пользователя, не обещаем бесплатные credits.

F: OpenAI публикует цены с различием input/cached/output и режимов. [S17] D: не закладывать фиксированный месячный расход по названию модели; записывать usage пилота и рассчитывать стоимость.

F: Docker документирует user, mounts, capabilities и network controls. [S18] D: non-root agent container и offline build; allowlist требует proxy/firewall. Контейнер без сети не может напрямую обращаться к API.

Никаких аккаунтных permissions, баланса, возможности платёжной карты или локальной работоспособности proxy не проверено. $0 API и наличие ключа — исходные условия пользователя.

## 8. Решение по итогам исследования

Продолжать проект с компактным MVP: bootstrap T0 уже подтверждён, его manifest и воспроизводимость остаются за B00/B01; следующий игровой срез — B02 с проверкой Def API. База без DLC; расчёты отдельно; state у Pawn через HediffComp; XML задаёт ступени и стандартные эффекты; Jobs выполняют практики; окно объясняет состояние; Harmony не нужен до доказанной необходимости.

Минимальный мод уже реализован, собран и загружен; gameplay-реализация и доказательство совместимости её API остаются следующими этапами. Утверждения «поддерживается1.7», «не ломает saves» и «удобнее конкурентов» должны стать результатами проверок, а не обещаниями этой документации.

### Новые риски и минимальные альтернативы

1. **Общий state не означает общий способ действий.** Непроверенный человеческий Job может сломать animal needs/AI. Альтернатива: действие ухаживающего колониста и пассивный сон, без новых animal Jobs.
2. **WorldPawn lifecycle и память.** Глобальный реестр может удерживать сотни диких зверей и блокировать mothball. Альтернатива: состояние на Pawn, no catch-up и временный индекс только активных на карте.
3. **Видовая совместимость.** У модовых животных могут отличаться тело, needs, гены и обучение. Альтернатива: 2–3 проверенных базовых вида и opt-in профили; unknown — dormant.
4. **Нагрузка и погрешность выборки.** Редкий tick не гарантирует малую нагрузку, если каждый раз сканировать карту. Альтернатива: простые условия сна и интервальные обновления ограниченного поднабора.
5. **Сила и экономика.** Размножение, долголетие, ядра и resurrection могут создать бесплатную армию/ферму. Альтернатива: не наследовать ранг, не менять fertility/продукты и отложить ядра/сильную генерацию.
6. **Миграции и расширение scope.** Ранняя универсальная иерархия может задержать MVP. Альтернатива: сохранить owner/поля v1, вынести только человеческий допуск из Core, новые данные вводить при их реальном выпуске.

### 10.4. Новые риски и минимальные ответы

- **Scope и зависимость от DLC:** пространственный аналог легко превращается в копию Biotech и незапланированный движок. Ответ: свой список кругов, без pollution calls/Defs, отдельные версии; 0.1.0 без инфраструктуры среды.
- **Старые saves и невидимые поля:** повторная генерация/потерянная ссылка создают опасную ауру. Ответ: D=0 по умолчанию для старых карт, initialized flag, один владелец, восстановление индекса и выключение missing building.
- **Stale cache и цена запросов:** actor движется внутри bucket, питание/overlay обновляются неправильно. Ответ: map+точная position+revision, invalidation и нагрузочная матрица; ограничение контента по результатам.
- **Неравенство и обход угрозы:** сильная зона становится бесплатной ловушкой для рейдов или вынуждает всех культивировать. Ответ: обратимый постепенный вред, нет стартовых Extreme-полей, управляемые безопасные участки, полный цикл при D=0, проверка боевого использования.
- **Stacking/энергия из ничего:** наставники/формации/звери ускоряются без предела. Ответ: max/min, общий cap поддержки, beast time cap; первый срез честно без conservation, резервы/сеть — отдельная экономика.
- **Дублированные таймеры/состояния:** общий updater может повторно начислять progress или превращать обычного Pawn в культиватора. Ответ: exposure отдельно, практика в прежних владельцах, snapshots только для чтения и независимые schemas.
- **Сложная биология/моды:** неизвестные race/plant trackers нельзя считать стандартными. Ответ: явные профили, default A/V=1 для поддержанных, отсутствие эффектов для неподдержанных и никаких изменений растений в первом срезе.
